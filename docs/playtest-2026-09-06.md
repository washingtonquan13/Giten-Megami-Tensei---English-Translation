# Play-test, 2026-09-06 — triage

Nine reports from an actual play session, with screenshots. What each one turned
out to be, and what is still open.

**The session was played on `dds_dev.exe`, and its trace survived.** The machine
lost power mid-session, but `play/en/ddswin/trace.bin` holds **150,019 complete
20-byte records with nothing torn** — the kernel had flushed all of it. That is
the first time this project has had a real play session on record, and it answers
several of these outright. Anything below citing token counts or character counts
comes from it.

Two things about the dev build matter here. It differs from `dds.exe` by
**exactly the three tracer call-site rel32s and the `.trc` section** — the English
content is identical, so nothing below is a dev-only artefact. But the copy in
`play/en` was built at 03:30 and was **missing every exe string fixed in
8c46197**, which is why items 3, 4 and 6 were real for this player. Both exes are
rebuilt and installed now.

My first theory — that a drifted overlay had stopped serving these files — is
**wrong, and the trace disproves it.** The overlay was working: `m/MS0059` ran
25.4% of its tokens on virtual PCs, `m/MS0017` 28.2%, `m/MS00DD` 14.0%. A virtual
PC is a thing only the overlay produces.

## What the exe scan settled

A pass over `.rdata`/`.data` for NUL-terminated cp932 strings, keeping only
those with two or more Japanese characters that something still addresses,
found 104 in `dds_org.exe`. Worth knowing for next time:

* 46 of the strings that *look* untranslated are the developers' own assertions
  — "臨海コロシアムの防具屋でない場合は連絡して下さい。Takubo" and 45 more like
  it, plus a note signed S.Iseki and one signed きたべ. They print only on paths
  the shipping game does not take. Leave them; they are a record of who wrote
  the shop code.
* Scanning `.text` as well is a waste of time: ordinary x86 decodes as kanji
  constantly, and every hit there was a false positive.
* `et/` has no untranslated text outside the tables. The 2,430 "characters"
  a naive scan finds in 13 `et/` files are binary fields decoding as kanji.


## The full-width digits — the one real defect the trace found

Every double-byte character the whole session fetched — 1,576 of them — came from
**the original file bytes, never from our overlay text**. So no English span
anywhere in that session contained a Japanese character; the corpus is clean on
this. What the player was seeing is narrower and more specific than "the grammar
is off":

> `４７ HP of damage`

**559 of the 858 stray characters in the battle-message files are full-width
digits and full-width spaces.** The engine renders every number the `{03:xx}`
macro expands as zenkaku, which was right for a Japanese game and reads as a
font glitch inside an English sentence. The rest are demon attack names — 甘い息
(Sweet Breath), 体当たり (Tackle) and about 90 other characters — which are **not
stored as plain text in any game file**: a byte search for them across `m/`,
`et/`, `p/`, `fc/` and the exe finds nothing, so they are assembled at runtime
from something the pipeline does not model yet.

Neither is fixed. The digits need the engine's number formatter, which is not a
string edit — there is no `０１２３４５６７８９` table in the image (the only
zenkaku digits in `.data` are the debug menu's own `＋１０`/`－１００` labels), so
it converts arithmetically and the routine has to be found by disassembly. That
makes it a **rendering change**, which is the same category as the two
non-translation exe edits in `docs/exe-patches.md` and is worth agreeing before
doing rather than after.

## Reading a trace, for next time

* A **virtual PC** (`pc0 >= image_end`, and `image_end` comes from the overlay
  directory) is produced by nothing but the overlay, so the share of virtual
  tokens per file is a direct yes/no on whether English was served — no guessing
  from screenshots.
* Reconstructing the character stream from the `ch` field says what was *on
  screen*, which is the question screenshots answer and static coverage numbers
  do not. `m/MS0059` looked untranslated to the player and was 100% English.
* `trace selfcheck` reporting 22,584 of 150,019 records whose bytes "do not match
  the build" is **expected, not an error**, when the trace ran with an overlay and
  the check is against the Japanese `m/`. The mismatch rate tracks the served
  share.
* Two file ids in the trace have no `m/MS####.BIN`: `0x00FF` (2,812 tokens) and
  `0x007F` (470). Both logged `flags=0`, so the interpreter context was *not*
  null and they are not the known stale-context case. Unexplained; not chased.
