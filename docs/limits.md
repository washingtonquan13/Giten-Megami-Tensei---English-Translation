# What the tooling does not know

Every re-adopted module carries an entry here.  An entry is closed only by evidence from the exe or the tracer, never by a plausible theory.

## container / records
- **A record may not exceed 32,767 bytes** (closed 2026-09-04 by the tracer + disassembly of the loader `0x43ABC0`: the per-record growth delta is a signed 16-bit value; over 0x7FFF it goes negative, the shrink path runs and the game crashes on load).  The original's largest record is `m/MS006A` r00 at 28,291 bytes -- the BBS -- so English there has 4,476 bytes of headroom.  Enforced by `check` (`record-size`, predicted from the tables) and `audit` (measured on the build).
- Record-count words that overstate the body (`m/MS600A`, `m/MS610B`, `et/ID00A2`, `et/ID00A3`) and trailing bytes are copied verbatim; what the engine does with them is unknown.
- Containers with duplicate record ids and branches (`m/MS6000` c0/1/8, `m/MS6800` c0, `m/MS610B` c15) are not editable.

## vmops / opcodes.json
- 267 opcodes are typed as consuming no operands because the static tracer took the fall-through; 148 records cannot be tiled (123 before the switch grammar; the 25 newly refused ones tiled by luck and were editable).  `1F82` is a known offender: its operand model eats the next opcode's `1F` prefix (`m/MS0002` r26, `m/MS0015` r02, `m/MS0032` r22).
- ~~`1F01 nn` followed by `00`: meaning unknown.~~ **Closed 2026-09-04 by trace:** `1F01 nn` prints runtime string *nn* -- `00` is the player's name (the trace shows the PC jump to offset 0 of the name buffer and read 葛城史人), other indices print counters (`６`). The `00` after it is that string's terminator. v0.05 stripped all 3,240 and hard-coded names; we keep them.
- ~~The byte after a name macro in the post-menu dead zone (`00 02 01 6a`): meaning unknown.~~ **Closed 2026-09-04:** those bytes are a switch-table case (`[case 02][kind 01][rel16]`, format-notes 2.12) that the old five-byte model for `0F` had spilled into the text.  They are operands now and never reach a table.
- Switch tables (`0E`/`0F` and 14 relatives) are decoded from the handler; a `kind` byte other than 0/1 refuses the record.  Which records those are is known (25 that used to tile by luck), what their real layout is, is not.
- `NOT_A_BRANCH = {010, 011, 182}` is statistical (target lands on an instruction at or below chance).  `017` is in the grey zone on the original (48.7% vs chance 43%) and is still relocated.
- ~~Our expression model disagrees with the engine for 67 of 94 selectors.~~ **Closed 2026-09-06: it does not.  The extraction was wrong, twice over.**  `tools/extract_expr_nodes.py` carried its own control-flow walker which, on a `call`, compared the target against the readers it knew and otherwise stepped *over* it — so every kind handler that reads through a helper reported "consumes nothing".  Kind `0x0D` (selectors `19`–`23`) is the proof: `0x00436C49` calls `0x00438C40`, which is `call READ_U8; call READ_EXPR_DEREF`, i.e. `u8 + expr` — exactly what `opcodes.json` already said.  Separately, **there is a third stream reader, `0x00438FE0` (4 bytes, fetcher `0x438EC0`)**, alongside `0x00438FA0` (1, `0x438E50`) and `0x00438FC0` (2, `0x438E80`); not knowing it made selector `0x02` look like a leaf when it is a `u32`.  Following delegation and counting all three readers, the engine agrees with `opcodes.json` for **94 of 94 selectors** (see the next entry for the last two).  The extractor now reuses `tools/opcode_operands.py`'s walker instead of keeping a second one that could drift.
- ~~Selectors `0x4B` and `0x4F` are context-dependent in the engine.~~ **Closed 2026-09-06: they are not, and the expression model is complete at 94/94.**  A third walker bug: an indirect `jmp *0xTABLE(,%reg,4)` was followed as if the table address were a code target, so it decoded jump-table *data* into paths that consumed bytes nothing consumes.  Their callees (`0x00437440`, `0x004373E0`) are `movswl 0x4(%esp); cmp $3; jmp *table` — a dispatch on the value the caller already read, taking **nothing** from the script stream.  Both selectors are one `expr`, as `opcodes.json` said.  The walker now reads the jump table out of the image and follows every entry.
- ~~`tools/opcode_operands.py`'s `_at()` is order-dependent~~ **Fixed 2026-09-06.**  It answered from any previously-cached 0x200-byte linear sweep containing the address, but a sweep runs off the end of small functions into padding and drifts, so the answer depended on what had been walked first — selector `0x59` read as a leaf in a full run and as `u8 + expr` when walked first in a fresh process.  It now decodes from the nearest *proven* instruction boundary, and boundaries are recorded as control flow proves them.  Three walker bugs were found in one day (step-over-calls, cache order, indirect-jump targets); treat a surprising result from it as suspect until the disassembly is read.
- The expression table was **not** what blocks the untiled records, and neither is the switch grammar.
- **Switch tables are fully statically determinable: a table is always `4N + 1` bytes** (verified 2026-09-06 from `0x004327C0`).  `cmpw $0x0,0x14(%esp); je 0x432845` is *not* an early-out — it selects a second, parallel loop with the **identical** byte layout, differing only in the match test: mode `0` takes the first case whose key is `>=` the selector (cumulative threshold, right for `0E`'s 1..100 roll), mode `1` takes exact equality (right for `0F`'s menu byte).  Neither mode skips the table, and neither early-exits on a match, so the PC afterwards is always `table_start + 4N + 1`.  The mode is a literal `push` immediate at all nine trampolines and is never computed, and it does not affect length, so a tokenizer never needs to know it.  Case layout `[u8 key][u8 kind][u16 payload]`, `kind == 0` → `[u8 file][u8 rec]` via `0x00433C10` (two `READ_U8`, branchless), else rel16 via `0x00433EC0` (one `READ_U16`; it also confirms `rel16_target = pc_after_operand + imm16` directly).  `vmops._read_switch` was already correct.
- `_read_switch` refuses `kind > 1`.  That is **not** VM-faithful — the handler only tests `kind != 0` — but the compiler emitted only 0 and 1, and every record the guard rejects proves to be desynced anyway (kinds 16/174/240/227, non-ascending keys).  It is kept deliberately as a desync detector: dropping it converts loud failures into silent mistilings.
- The 26 remaining switch failures are **runaway walks with an upstream cause**, not switch-decoding problems.  Clean tables average 2.4 cases with 98.8% of kinds in {0,1} and 99.1% ascending keys; the failing ones average 40.4 cases, 21.1%, and 8.0% — they are random record bytes.  All 52 belong to `0x00E`/`0x00F`, single-byte opcodes with no pre-operands, so the table's start cannot be mis-modelled: the walk arrived at a byte that was never an opcode.  Corroboration that the 4-byte stride is right: of 5,365 rel16 fields inside cleanly-walked tables, 99.22% land on a legal instruction boundary, better than ordinary branch rel16s (98.52%, n=19,956).
- **Engine boundary agreement was measuring the wrong denominator; the opcode model now has *zero* known disagreements on the traced routes.** `1F01` prints a party-member name by reading it through the same byte fetch the tracer hooks, but out of a *string buffer*: the PC restarts at 0 and counts up in twos, one event per character, then execution resumes just past the `1F01` token. Verified end to end at `m/MS0017` r02 0x9E (`1f 01 00 00 04 ff`, four events spelling 葛城史人, resume at 0xA6) and across all 74 runs: every pc is even and ≤ 8, every character decodes as cp932, and the strings are 葛城史人 / 橘由宇香 / a counter. **No record holds those addresses**, so scoring them against our tokenisation said nothing about the model -- and it is the whole reason the figure sat at 98.4%. `giten/trace/core.py` now classifies them (`NAME_KIND`), strictly: a `1F01` token must sit on one side of the run, the body must be even PCs ascending from 2 that decode, and execution must resume inside a record. Of 18,683 events on `jp2` + `jp-friends`: 252 name-buffer, **0 model errors**, 29 script-end (a v1 tracer limitation -- it read the context after `exec_token` returned and the engine had already cleared it; v2's `pc0` fixes it, but no v2 trace has ever been captured), and 10 excursions no `1F01` bounds, left as disagreements because their cause is unproven (`m/MS00D8` r00; the token before them is `1F86`, which is `push $1; push $1; call 0x00434740` -- a conditional branch, so it cannot be the printer, and the RECID logged there is stale). **So "pull on the opcode model to raise agreement" is finished work: the ceiling it can reach is the number it is already at.**
- A decoder bug found in the same pass: `locate` rule 1 accepted *any* text token ending at the logged pc without checking the character, which shadowed rule 2 (a branch landing on that pc). At `m/MS7F04` r07 0x2A the engine had jumped onto the `18` opcode starting there and the two text bytes ending there were charged with the disagreement. Those were the last 3 "model" errors and they were never the model.
- **`1E C4` reads one expression, not two** (fixed 2026-09-06). Found with no trace and no playing: of 25,346 rel16 targets corpus-wide, 25 do not land on a token boundary, and one of those is in `m/MS00D8` r05 -- a record the engine executed 187 times on the traced routes. `1E C4`'s trampoline is `push $1; call 0x00433860`, which forwards to `0x004335E0`: that reads two u8 (`0x004335A0`), then calls `0x004335C0`, which reads an expression **only when its argument is 0**, then always reads one more. Mode 1 therefore takes `u8 u8 expr` = 6 bytes, and 0x25 + 6 = 0x2B is exactly the branch target that missed. Its sibling `1E C3` is the same shape with mode **0** and does read both, so the table was right for it -- that pairing is the control. Same family as the `0x14C`-`0x151` fix, missed because it reaches `0x004335E0` through an extra hop. `ok`/`stray`/`unimpl`/`untiled`/`impossible` all unchanged; engine boundary agreement 98.40% -> 98.43% on `jp2`/`jp-friends`.
- **`tools/opcode_operands.py` reports operand *counts*, never order.** `spec()` emits `["u8"]*a + ["u16"]*b + ["u32"]*u + ["expr"]*c`, so any opcode whose real layout is not u8s-then-u16s-then-exprs is printed as a mismatch. `0x00B` is the worked example: the tool says `u8,u8,u16` against the table's `rel16,u8,u8` and looks like a bug, but `0x00430008` is `push $1; push $0; call 0x00434850`, whose first call `0x00434680` is `jmp 0x00433EC0` -- the rel16 reader -- before `0x00434780` reads the pair. The table is right. The corpus says so too: with the displacement in the first slot 1,263 of 1,267 targets land, with it last only 46 of 96 do and 1,174 fall out of the record entirely.
- **Two disproven hypotheses, recorded so they are not re-tried.** (a) *`1F0D`/`1F0E` take no operand.* The bytes look like it -- `1f 0d 1f e5` reads naturally as two opcodes, and it moves `untiled` 74 -> 38 -- but the handler walk says both read an expression, and `impossible`, the counter that cannot improve by accident, gets **worse** (43 -> 50). Rejected. (b) *Expression selector `0x02` is a u16.* It scores better on the branch oracle (25 misses -> 13), but selector `0x02`'s handler `0x00436B3B` calls `0x00438FE0`, which is `0x00438EC0` = two u16 fetches with the second shifted left 16, i.e. a real u32. The gain is an accident: `0x02` occurs 13 times in the whole corpus, 12 of them in `m/MS6F00`/`m/MS6F1F` (byte-identical duplicates), and 10 of the 12 "fixed" misses are in records that never tiled. A rare selector shortened by two bytes reshuffles boundaries in already-broken records. **The branch-landing oracle can flatter exactly like `stray` and `overrun`; check whether the records it fixes were sound to begin with.**
- **The other 24 boundary misses are in records nothing has ever executed.** `m/MS610D`, `m/MS6200`, `m/MS6F00`, `m/MS6F1F` contribute 0 traced events between them, and `m/MS6F00`/`m/MS6F1F` are byte-identical, so 25 sites are 17 distinct and 16 of those are unexecuted. Whether they are code the routes never reach or data tokenised as code is open; the `1E C4` result shows the branch oracle can settle such a case when the record is real code, and the `0x02` result shows it cannot be trusted alone when the record is not.
- **The tag-`00` spans that reach the `japanese` rule are data, not text -- but not one kind of data.** Two were run down on 2026-09-06 and neither is "garbage" in the sense of meaningless bytes:
  - `m/MS0007` r35 and its siblings (`ｮｭｱｲｳ`, one half-width kana per span): `1FA7` at 0x0192 is typed `rel16 + expr + expr` and consumes 8 bytes, but the site is `1f a7 | 91 01 | 00 b0 00 af 00 ae 00 ad 00 b1 00 b2 00 b3 | 04 ff` -- a **variable-length list**, of which the model claims the first two entries and the other five become NUL-opcodes and one-byte "text". The values `b0 af ae ad b1 b2` are the same ids the neighbouring `1F60 00 XX` opcodes take, so they are operands beyond doubt. Same shape as the `0x103`/`0x104` fix (a list where the table claimed a fixed count).
  - `m/MS001F` r02 (`辞書５`, `{01:00}`, `{04:FF}`, `d`): 11 bytes sit between two `1E BE` tokens (`1e be 00 01 72 | 01 00 00 00 06 00 00 04 ff 00 64 | 1e be 01 03 05`). `1E BE` is typed 3 u8, fixed size 5, and the walk *does* consume exactly that -- so unlike `1FA7` the fault is not a short read of a known opcode; nothing claims those 11 bytes at all. Cause not yet named. `m/MS002B` r02[89] (`d{03:00}`) and `m/MS0059` r04[19] (`{03:00}d`) are the same run.
  - Consequence for the tables: **`m/MS7F05` is a dead dictionary.** It holds exactly one entry, `辞書５` ("Dictionary 5"), and all 7 apparent `{06:xx}` calls in the corpus are the `06 00` of that data run being rendered as a pool call. Nothing on screen ever prints it, so it is deliberately left untranslated.
  - The engine trace cannot adjudicate any of this yet: none of these records has ever been executed on a traced route (`m/MS001F` has 3,603 traced events, all in record 5). Raising boundary agreement above today's 96.83% would settle them only for records the routes actually reach -- for these, the next step is either the `1FA7`/`1EBE` handlers under `tools/opcode_operands.py`, or a route that enters them.

## codec
- One span in the original (`m/MS0061` 0:0B[32]) contains `FA 82` (冾, IBM extension); cp932 re-encodes it as the NEC duplicate `ED 65`.  Text tokens that do not re-encode to their own bytes are rendered as raw `{=HH}` tokens.

## script / relocation
- ~~Branches whose target is strictly inside an edited span block the edit (115 lines ship untranslated).~~  **Partly closed 2026-09-06.**  Of 322 such targets corpus-wide, 144 point at the span's own trailing `1E 10` page wait and 7 at a trailing `0A` -- a branch that skips the words and goes straight to the page break.  A translation keeps those escapes verbatim, so the last *k* bytes survive the edit and the target still exists *k* bytes from the end; `_rebuild_record` now anchors it there and the edit ships.  **37 finished lines that were written and not reaching the screen now do.**  The remaining **71** are branches into actual prose, where the English genuinely has no such byte -- those are still refused, and the honest fix for them is to split the span at the target so each fragment is separately translatable (the translator then has to write text that reads correctly both with and without the skipped part, as was done by hand for `m/MS0002` 0:27).  `verify` reports 0 tiling regressions.
- Text-capture mode (`1B`..`1C`, 256-byte buffer) is enforced by `check` (`capture`) from the static token walk; a region entered by a branch from elsewhere is not modelled.

## exe
- Debug-menu arming is unverified (the table at `0x468318` is not four contiguous pointers).
- `HKCU\Software\ASCII\GITEN_DDS\DevConfig` must exist at startup; written by `Config.exe`.

## overlay (runtime translation)
- Spans are diverted only when entered at their first byte; a branch landing inside a translated span shows the Japanese tail (same 115 lines `@noedit` blocks).
- `et/ID*` tables are read by other code paths, not the interpreter fetch; the hook does not cover them.
- Not yet play-tested as of 2026-09-04 evening; `docs/overlay.md` has the test setup.
