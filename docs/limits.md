# What the tooling does not know

Every re-adopted module carries an entry here.  An entry is closed only by evidence from the exe or the tracer, never by a plausible theory.

## container / records
- **A record may not exceed 32,767 bytes** (closed 2026-09-04 by the tracer + disassembly of the loader `0x43ABC0`: the per-record growth delta is a signed 16-bit value; over 0x7FFF it goes negative, the shrink path runs and the game crashes on load).  The original's largest record is `m/MS006A` r00 at 28,291 bytes -- the BBS -- so English there has 4,476 bytes of headroom.  Enforced by `check` (`record-size`, predicted from the tables) and `audit` (measured on the build).
- Record-count words that overstate the body (`m/MS600A`, `m/MS610B`, `et/ID00A2`, `et/ID00A3`) and trailing bytes are copied verbatim; what the engine does with them is unknown.
- Containers with duplicate record ids and branches (`m/MS6000` c0/1/8, `m/MS6800` c0, `m/MS610B` c15) are not editable.

## vmops / opcodes.json
- 267 opcodes are typed as consuming no operands because the static tracer took the fall-through; 148 records cannot be tiled (123 before the switch grammar; the 25 newly refused ones tiled by luck and were editable).  `1F82` is a known offender: its operand model eats the next opcode's `1F` prefix (`m/MS0002` r26, `m/MS0015` r02, `m/MS0032` r22).
- ~~`1F01 nn` followed by `00`: meaning unknown.~~ **Closed 2026-09-04 by trace:** `1F01 nn` prints runtime string *nn* -- `00` is the player's name (the trace shows the PC jump to offset 0 of the name buffer and read 葛城史人), other indices print counters (`６`). The `00` after it is that string's terminator. v0.05 stripped all 3,240 and hard-coded names; we keep them.
- ~~The byte after a name macro in the post-menu dead zone (`00 02 01 6a`): meaning unknown.~~ **Closed 2026-09-04:** those bytes are a switch-table case (`[case 02][kind 01][rel16]`, format-notes 2.12) that the old five-byte model for `0F` had spilled into the text.  They are operands now and never reach a table.
- Switch tables (`0E`/`0F` and 14 relatives) are decoded from the handler; a `kind` byte other than 0/1 refuses the record.  Which records those are is known (25 that used to tile by luck), what their real layout is, is not.
- `NOT_A_BRANCH = {010, 011, 182}` is statistical (target lands on an instruction at or below chance).  `017` is in the grey zone on the original (48.7% vs chance 43%) and is still relocated.
- ~~Our expression model disagrees with the engine for 67 of 94 selectors.~~ **Closed 2026-09-06: it does not.  The extraction was wrong, twice over.**  `tools/extract_expr_nodes.py` carried its own control-flow walker which, on a `call`, compared the target against the readers it knew and otherwise stepped *over* it — so every kind handler that reads through a helper reported "consumes nothing".  Kind `0x0D` (selectors `19`–`23`) is the proof: `0x00436C49` calls `0x00438C40`, which is `call READ_U8; call READ_EXPR_DEREF`, i.e. `u8 + expr` — exactly what `opcodes.json` already said.  Separately, **there is a third stream reader, `0x00438FE0` (4 bytes, fetcher `0x438EC0`)**, alongside `0x00438FA0` (1, `0x438E50`) and `0x00438FC0` (2, `0x438E80`); not knowing it made selector `0x02` look like a leaf when it is a `u32`.  Following delegation and counting all three readers, the engine agrees with `opcodes.json` for **94 of 94 selectors** (see the next entry for the last two).  The extractor now reuses `tools/opcode_operands.py`'s walker instead of keeping a second one that could drift.
- ~~Selectors `0x4B` and `0x4F` are context-dependent in the engine.~~ **Closed 2026-09-06: they are not, and the expression model is complete at 94/94.**  A third walker bug: an indirect `jmp *0xTABLE(,%reg,4)` was followed as if the table address were a code target, so it decoded jump-table *data* into paths that consumed bytes nothing consumes.  Their callees (`0x00437440`, `0x004373E0`) are `movswl 0x4(%esp); cmp $3; jmp *table` — a dispatch on the value the caller already read, taking **nothing** from the script stream.  Both selectors are one `expr`, as `opcodes.json` said.  The walker now reads the jump table out of the image and follows every entry.
- ~~`tools/opcode_operands.py`'s `_at()` is order-dependent~~ **Fixed 2026-09-06.**  It answered from any previously-cached 0x200-byte linear sweep containing the address, but a sweep runs off the end of small functions into padding and drifts, so the answer depended on what had been walked first — selector `0x59` read as a leaf in a full run and as `u8 + expr` when walked first in a fresh process.  It now decodes from the nearest *proven* instruction boundary, and boundaries are recorded as control flow proves them.  Three walker bugs were found in one day (step-over-calls, cache order, indirect-jump targets); treat a surprising result from it as suspect until the disassembly is read.
- The expression table was **not** what blocks the untiled records, and neither is the switch grammar.
- **Switch tables are fully statically determinable: a table is always `4N + 1` bytes** (verified 2026-09-06 from `0x004327C0`).  `cmpw $0x0,0x14(%esp); je 0x432845` is *not* an early-out — it selects a second, parallel loop with the **identical** byte layout, differing only in the match test: mode `0` takes the first case whose key is `>=` the selector (cumulative threshold, right for `0E`'s 1..100 roll), mode `1` takes exact equality (right for `0F`'s menu byte).  Neither mode skips the table, and neither early-exits on a match, so the PC afterwards is always `table_start + 4N + 1`.  The mode is a literal `push` immediate at all nine trampolines and is never computed, and it does not affect length, so a tokenizer never needs to know it.  Case layout `[u8 key][u8 kind][u16 payload]`, `kind == 0` → `[u8 file][u8 rec]` via `0x00433C10` (two `READ_U8`, branchless), else rel16 via `0x00433EC0` (one `READ_U16`; it also confirms `rel16_target = pc_after_operand + imm16` directly).  `vmops._read_switch` was already correct.
- `_read_switch` refuses `kind > 1`.  That is **not** VM-faithful — the handler only tests `kind != 0` — but the compiler emitted only 0 and 1, and every record the guard rejects proves to be desynced anyway (kinds 16/174/240/227, non-ascending keys).  It is kept deliberately as a desync detector: dropping it converts loud failures into silent mistilings.
- The 26 remaining switch failures are **runaway walks with an upstream cause**, not switch-decoding problems.  Clean tables average 2.4 cases with 98.8% of kinds in {0,1} and 99.1% ascending keys; the failing ones average 40.4 cases, 21.1%, and 8.0% — they are random record bytes.  All 52 belong to `0x00E`/`0x00F`, single-byte opcodes with no pre-operands, so the table's start cannot be mis-modelled: the walk arrived at a byte that was never an opcode.  Corroboration that the 4-byte stride is right: of 5,365 rel16 fields inside cleanly-walked tables, 99.22% land on a legal instruction boundary, better than ordinary branch rel16s (98.52%, n=19,956).
- **Opcode `10` vs `1F 00` (2026-09-06; superseded later the same day -- the headline was backwards, see the dispatcher entries below).** `10` was the loudest lead -- 26 of its 55 expressions impossible, and in `NOT_A_BRANCH` on statistical grounds -- but it is exonerated. Its dispatch entry reads exactly what the table says (one u16, one expr, `reads()` = `(0,1,0,1)`), which is **identical to `12`**, whose branches land 254 of 256. What separates them is what comes before: **42 of the 55 `10`s sit immediately after `1F 00`, and every one of the 16 testable misses is in that group.** Not one `10` following a known opcode misses. Resolved against the whole container image (records are contiguous at runtime, so a within-record test undercounts): `10` lands 15/55, `11` 8/59 -- read at the time as "not branches", which the disassembly later contradicts: `0x00433C40` writes the PC, so they are branches whose rel16 we are reading from mis-framed bytes. The same run clears a standing doubt: **`17` lands 62/62 against the image**, so the "grey zone, 48.7% vs chance 43%" note above is resolved in favour of relocating it.
- **`1F 00` is settled: it is exactly a two-byte no-op (2026-09-06, from the dispatcher).**  `0x0042FF50` is the opcode dispatcher -- the image's *only* reference to the table at `0x004318B0` -- and it indexes that table by the raw token value under `cmp $0x2fd; ja 0x4318aa`.  Table entries `1D`, `1E` and `1F` are the three escape prefixes: each reads **one** byte, adds `0x300`/`0x200`/`0x100`, re-checks the same `0x2FD` bound and re-dispatches.  So `1F nn` is index `0x100+nn` and two bytes; `1E nn` is `0x200+nn`; and `1D nn` is always past the bound, i.e. "eat one byte, do nothing".  `handler(0x100)` is `0x004318AA`, `xor ax,ax; pop esi; ret`.  The fetch path was then walked to the bottom and holds nothing extra: loop `0x00439090` -> `0x00439000` (pushback `0x00453BC0`, else `0x00438F50`) -> `0x00438F00`, which reads one byte and takes a second **only** when the `_ismbblead` bit `0x04` is set in the locale table at `0x00490C11` -> `0x00438E50`, a plain `[base + pc++]`.  There is nowhere for an unexplained byte to go.  The earlier note's other candidate, "`exec_token` handling `1F 00` before dispatching", is disproved: `exec_token` (`0x00439020`) receives an already-assembled token and fetches nothing itself.
- **RESOLVED by trace, 2026-09-06: opcode `10` is exactly what the tables say, at every site the engine reached.**  A warp build (`tools/make_warp.py`) sent the interpreter straight into `m/MS0031` r01 with no save and no playthrough.  Of 148 logged tokens with a usable start, **145 lengths match ours exactly and 0 engine starts fall off our boundaries**; the 3 that "differ" are branches (`0x104`, `0x011`, `0x018`) whose next PC is the branch target, and **all three targets land on one of our token boundaries**.  The disputed shapes agree byte for byte:

      @01F0  10 01 01 1f   ours 8 bytes   engine 8
      @0227  10 01 00 0f   ours 6 bytes   engine 6
      @022F  10 1f c1 00   ours 5 bytes   engine 5
      @02B9  10 01 01 8f   ours 4 bytes   engine 4

  `1F 00` was observed directly as a two-byte token (`pc0`/`pc` give 0x01EE..0x01EF), closing that from the engine as well as from the dispatcher.  **The "mid-word text" was never evidence of a bad parse**: `10` is a conditional jump, and at the `10 01 00 0f` sites its target is `PC_after_rel16 + 1`, i.e. exactly the byte where the full word starts.  Fall-through prints `ん、健康そのものだね。` and the taken branch prints `うん、健康そのものだね。` -- two variants of one line, not a tiling error.  `m/MS0031` r01 offsets 0x0108 and 0x0367 were not on the path this run took, but 0x0227 -- the same `10 01 00 0f` shape -- was.
- **`0x011` takes branches: observed.**  At `m/MS0031` r01 offset 0x0262 the engine executed `11 1f 00 08` and its next PC was 0x0284, a token boundary, where fall-through would have been 0x0266.  `script.NOT_A_BRANCH` still lists `0x010`/`0x011`; that list is a *tiling heuristic about the rel16 slot*, not a claim about the engine, and the disassembly (`0x004348B0` -> `0x00433EF0` -> `0x00433C40`, which writes the PC) already said so.

- **What actually breaks, restated correctly.**  It is not four bytes and it is not `1F 00`; it is one character at the `10` sites that follow `1F 00` (42 of 55).  Three shapes, and no single reading of `10` fits all three:

      `10 01 00 0f` x7   ours resumes `ん、健康...`      the text is `うん、健康...` at +4
      `10 01 01 82` x8   ours resumes `｢きなり、倒...`   the text is `いきなり、倒...` at +3
      `10 01 01 1f` x23  ours resumes at `ba` (`ｺ突然...`)  the text needs `1F BA` at +3

  At the `0f` sites +4 *is* the branch target (rel16 = 1), so "the engine takes the branch" would explain them; at the `01 01` sites the target is 260 bytes away, so neither path prints what is written there.  Against our framing everywhere: the branch decision at the `0f` sites would be read from **uninitialised stack** -- the expression value is `0xA482`, `0x004374A0` returns immediately for anything above `0x0E` without writing either out-param, and `0x004348B0` reserves both with a bare `sub $0x8,%esp`.  A shipped script does not decide a jump on uninitialised memory, so the engine is probably not at that PC at all.
- **The 11 `10 1f c1 00 03` sites are confirmed correct as we tile them**, by a different argument, and they are the reason not to shorten `10` globally: a three-byte reading would put the next token on `00`, and opcode `00` is `or ax,0xffff; pop esi; ret` -- the sentinel the interpreter loop tests with `test ax,ax; jge`, i.e. the record terminator.  Every one of those records would end there.  These 11 follow `07`, never `1F 00`.
- **The expression model is now proven against the engine, 94/94.**  `0x00436B00` reads a u8 selector, maps it through `0x00437380` (selector -> kind, 62 kinds) and jumps through `0x00437288` (kind -> handler); both tables are in the image, so every selector's shape is a fact.  Walking all 62 handlers reproduces `docs/opcodes.json`'s `expressions.nodes` for **all 94 selectors, with no disagreement** -- including `0x0F`, which is kind 12, handler `0x00436C33`, `call 0x00438FC0` = one `u16` (shared with `0x01` and all of `0x0D`-`0x18`).  This retires the "NOT yet trustworthy / disagreed with 67 of 94" caveat from the first pass, which was an artifact of a bad function-extent heuristic.  **Do not "fix" `10` or the expression table.**  The decisive experiment is unchanged and now sharper: one traced route through `m/MS0031`, asking only whether the engine's PC is ever equal to the offset of a `10` byte that follows `1F 00`.

Those three bytes are the opcode escapes *in opcode position*; the expression reader never treats them that way.  `0x00436B00` reads one raw byte and indexes the kind table at `0x00437380`, where selectors **`0x19`-`0x23` all map to kind 13**, handler `0x00436C49`, `['u8','expr']` -- so `1D` and `1E` are not distinguishable from `1C`, which the rule never objected to.  The corpus shows no anomaly either: counting the top-level selector of all 65,315 expression operands gives `19`:5 `1A`:11 `1B`:9 `1C`:14 **`1D`:13 `1E`:13 `1F`:57** `20`:8 `21`:16 `22`:29 -- `1D` and `1E` sit dead centre among their neighbours, and the rule's 83 "impossible" expressions were exactly 13+13+57, i.e. every top-level use of the three.  **Every lead it manufactured is void**: `1FE8` 34/1717, `1F53` 10/20, `1F54` 4/20, `1F0D` 3/742, `1F0E` 1/160, and -- the loudest and the one that sent the `1F 00` hunt down a false trail -- `10` at 26/55. - **Engine boundary agreement is 18,659 of 18,659 -- every locatable event, on every trace on disk (2026-09-06).**  Deduplicated (`jp-friends` and `jp-overlay` are the same capture; `jp2` duplicates `jp-leave`; the first trace `jp.bin` predates a fix and resolves against no build) and with the `1F01` name-buffer excursions excluded as before. - **RESOLVED by trace, 2026-09-06: expression kind 13 is `u8 + expr`, and the corpus was wrong.**  Selectors `0x19`-`0x23` reach `0x00436C49` -> `0x00438C40`, an unconditional `READ_U8` then an unconditional `read_expr`.  The corpus argued the other way -- making kind 13 `['u8']` fixed 41 records and broke 1 -- and that change **must not be made**. Under `['u8']` the token would be five bytes.  `docs/opcodes.json` is right; the 41 records remain untiled for some other reason, and that reason is now unknown again.

- **The `0x004335E0` family is now complete: 22 entries, 11 per mode (2026-09-06).**  The worker reads two u8 via `0x004335A0`, then `0x004335C0` -- which reads an expression **only when its argument is 0** -- then always one more.  Every entry reaching it is `push <mode>; call <thunk>` with the mode a literal, so mode 0 is `u8 u8 expr expr` and mode 1 is `u8 u8 expr`.  `1E C4` was corrected this way, then `0x14C`-`0x151`; **`0x152`-`0x155` were missed** -- six of the ten mode-1 entries fixed, four left carrying an expression the engine never reads.  No counter noticed, because those records still *tiled*.  The witness is `m/MS00DB` c0 r28: six iterations of one block, byte for byte identical except a counter running `16 15 14 13 12 11`, **exactly 25 bytes apart**.  One iteration sums to 25 only when `0x153` is six bytes; the old model spent 29 and the walk read the loop counters themselves as opcodes `0x15 0x14 0x13 0x12 0x11`.  Found by sweeping the dispatch table for the *shape* rather than by chasing the record, and the same sweep says **no other worker+mode group disagrees** (421 groups; the single flag, `0x236` vs `0x23B`, is a false positive -- they share only `0x00438FC0`, the u16 reader itself). - **Every opcode the game actually uses, checked against the engine: 400 walked, 0 real disagreements (2026-09-06).**  The corpus uses 400 of the 766 dispatch entries.  Walking each one's handler gives **303 agreeing with `docs/opcodes.json`**, 17 whose shape is hand-modelled and not expressible as a read count (`switch`, `rtstr`, `pairs_ff`, `wait`), 79 the walker cannot resolve to a single shape (context-dependent handlers -- the `0x004335E0` family is the worked example of what hides there), and **one flag, `0x2D6`, which is a walker artifact, not a model error**: its handler is `call 0x004345A0`, and `0x004345A0` is `movw $1, 0x004712C8; ret` -- it reads nothing.  The walk misaligned on that 10-byte `movw`, ran past the `ret` into the next function at `0x004345B0`, and reported `u8 expr expr`.  The corpus agrees with us instead: 3 of the 4 sites are `1e d6 00` with the `00` terminator at the record's end, leaving no room for operands.  So `0x2D6` stays `[]`.
- **Run the walker in a fresh process per opcode.**  Its `_CACHE`/`_ENTRIES` accumulate and change `_at()`'s decoding base, so a long in-process run gives answers that depend on what was walked first -- the module's own docstring records selector 0x59 reading as a leaf in a full run and as `u8 + expr` when walked first.  A single loop over 400 opcodes also grew past a gigabyte and never finished, and disassembling the whole `.text` once instead is worse (every jump target resolves, so walks run away -- 7.6 GB).  One subprocess per opcode, six in parallel, finishes all 400 in 31 minutes; most take 2-4 s and the pool-call family (`0x001`-`0x008`) takes ~36 s each.
- **`@dupid` was blocking the wrong containers, in both directions (2026-09-06).**  The duplicates are real, not a framing artifact: every affected container's declared record count equals the number parsed, with zero trailing bytes and no error.  Most are duplicated *empty* slots -- a one-byte record holding `00`, the absent-length marker, emitted twice (13 such pairs in `m/MS6000` c15 alone); those are inert whichever one the loader keeps.  Four containers have a genuine conflict, and in three of them one side is a stub: `m/MS6000` c8 id 0x08 is a 137-byte record at stored position 8 and a 1-byte `00` at position 41; `m/MS610B` c15 id 0x8A is `1f 0d 00 00` at position 87 and 「ぬくもりを‥‥くれ」 at 139; `m/MS6012` c4 id 0x14 is a 12-byte fragment at position 20 and 「貴方の事を　見損…」 at 169; `m/MS6800` c0 id 0x0E is two near-identical opcode runs.
  The old rule blocked a container **if it contained a `rel16`**, reasoning that only a branch is measured against `base(id)`.  That is the wrong question and it was wrong both ways.  An overlay span's runtime address is `base(id) + offset` whether or not anything branches, so `m/MS6012` c4 -- whose duplicate shifts **235 of 256 bases by up to 16 bytes** -- was editable; while `m/MS6000` c0 and c1, whose duplicated ids are one byte each and byte-identical so that **0 of 256 bases move either way**, were blocked, holding 502 characters and 109 finished translations out of the byte build.  The predicate is now `records.layout_is_ambiguous`: resolve the ids first-wins and last-wins and ask whether *anything* differs (and refuse same-length copies whose bytes differ, which the corpus does not currently contain).  Effect: identity build still 844/844, the byte build applies **+111 spans** (115 unblocked less 4 newly blocked, exactly), `audit` unchanged at its one known finding, `check` errors 1,495 -> 1,384 with `width`/`width-choice` untouched, and no translation lost.
- **RETRACTED, same day: the duplicate-id question is not a shipping hazard, and does not need settling.**  I wrote that the overlay serving 164 spans out of layout-ambiguous containers was an open risk, and recommended a traced demon conversation to decide first-wins vs last-wins.  That was wrong -- the overlay is **fail-safe here by construction**, and reading `giten/exe/hook.c` shows it: the hook computes `fnv1a(base, FP_BYTES)` over the **live** record index the engine actually built, with `FP_BYTES = 0x400`, the whole 256-entry index, and applies a container's spans only when `dirs[i].fid == fid && dirs[i].fp == fp`.  Our fingerprint comes from `overlay.engine_index`, i.e. from the first-wins model.  So if the loader resolved a duplicate the other way, its live index would differ, the hash would not match, and the overlay would simply decline that container.  Verified for all four: first-wins and last-wins hash differently in every case (`m/MS6000` c8 `0x6098ED4D`/`0x87B507BF`, `m/MS6012` c4 `0x603B5ED6`/`0x81A9D411`, `m/MS610B` c15 `0x90E8B5B4`/`0x5AD80679`, `m/MS6800` c0 `0xBE32E104`/`0x1E5B2A78`).  The worst case is therefore **cosmetic**: 164 spans, 149 of them already translated, silently stay Japanese -- and that is visible by just looking at the screen.  It cannot corrupt an address.  Pinned by `test_the_overlay_fingerprint_catches_a_wrong_duplicate_resolution`.  Demon conversation needs the D.D.C (`m/MS0058` r00: 「Ｄ.Ｄ.Ｃは悪魔と会話する事を可能にする、言わば翻訳用プログラムよ」), so reaching those files costs a real play session -- and there is now no reason to spend it on this.

- **Why the untiled records were untiled: our tokenizer stops at a record boundary and the engine does not (2026-09-06).**  `base(id) = 0x400 + sum of the record lengths`, so records sit contiguously at runtime, and the byte fetch `0x00438E50` is a plain `[base + pc++]` with **no bound**.  A record's final token therefore reads on into the next record perfectly legally, and the record layer is an *index* into one image, not a limit on the walk.  Of the 78 records that refused to tile, **64 complete within seven bytes of lookahead** -- 21 at +1, 16 at +2, 21 at +3, the rest by +7 -- and the straddling token is nearly always control flow emitted at the end of a chunk: `10`, `14`, `16`, `18` or `1F 0D`/`0E`/`0F`.  `m/MS0031` r17 is typical: it ends `1F 00 10 01 01 00` and `10`'s expression wants one more byte.  Implemented as `partial.tokenize_straddling`, accepted only when the walk is otherwise complete (every token but the last ends inside the record, the last starts inside and finishes outside).  **Untiled records 78 -> 14**, and locked text **0.567% -> 0.480%** of the game's Japanese.
- **A straddling record keeps `tokens` None on purpose.**  The first cut put the tokens on `Rec.tokens`, and that was wrong in a way `audit` caught within one run: `_relocate` then rewrote `m/MS0031` r0D's rel16 (`14 ff 00` -> `14 ed 00`) and the audit reported the branch target moving.  A straddling token reads its operand bytes out of the *next* record, so its displacement is not something the relocator can reason about.  The tokens now live in `Rec.straddle_tokens`, reached through `Rec.span_tokens`, which only span resolution and the overlay consult; `tokens` stays `None`, so the byte builder, `_relocate` and `audit` go on treating the record exactly as untiled.  Verified rather than argued: a build with the rule disabled and a build with it enabled are **byte-identical**, `audit` is back to its single known finding, and the identity build is still 844/844.  Prefix tiling still wins for the one file that opts into it (`m/MS0080`) -- letting `@straddle` preempt it renumbered that file's spans and stranded rows.
- **The 14 that still refuse are a different failure.**  Nine hit the `0E`/`0F` switch-table kind guard, which `limits.md` already describes as a desync detector -- the walk arrived at a byte that was never an opcode, so the cause is upstream in the record; the rest are `unterminated pairs_ff` or an expression payload past the end that no lookahead completes.  `m/MS6F00` and `m/MS6F1F` are byte-identical, so it is really 12 distinct records: `m/MS0031` r00/r0B, `m/MS0080` r04, `m/MS610D` r1B/rCE, `m/MS6200` r16/r1F/r55/r4F, `m/MS6500` rC7, `m/MS6F00` r01/r1B.
- **The remaining locked text is not one thing.**  Of 0.480%: **0.147%** (624 characters, 40 rows) is those 14 records, and **0.333%** (1,414 characters, 278 rows) is `@dupid` -- containers where two records share an id, which makes `base(id)` and every branch measured against it ambiguous.  That second half is a hazard in the game's own data, deliberately blocked, and is not a gap in the model.
- **`0C` and `0D` are cross-record control flow: goto-record and call-record (2026-09-06).**  Both are `push <mode>; call 0x00433E70`, which reads a `[u8 file][u8 record]` pair via `0x00433C10` (two `READ_U8`, branchless -- the same reader the `0E`/`0F` switch tables use for `kind == 0`) and then branches on the mode: **`0C` (mode 0) -> `0x00433D70`, jump to that record; `0D` (mode 1) -> `0x00433E40`, which saves position via `0x0043C1F0` first and then jumps -- a call.**  `0x00433D70` carries special cases keyed on the pair (`file 0xDE record 1` becomes record 9, and others), so it is the real entry point for record dispatch.  Two consequences worth having: a record ending in `0C` ends for good, which is why 14 of `m/MS610D`'s tiling records finish on a three-byte `0C` token; and reachability inside a record cannot be decided from branches alone, because `0D` leaves and comes back.  It also means the `m/MS610D` tails after a `0D` are **reachable**, so "those bytes are dead" is not an escape from the kind-13 conflict above.
- **A record that tiles can still be tiled wrongly, and unrolled loops do NOT detect it (tried and disproved, 2026-09-06).**  `m/MS00DB` r28 tiled cleanly under a model four bytes long per iteration, and nothing in `ok`/`stray`/`unimpl`/`overrun` moved.  The obvious invariant -- a block repeated at a fixed stride must be tokenised the same way every period -- was built and run: find n-grams recurring at constant stride whose blocks differ only at the same one or two positions (a counter), then require either (A) token boundaries congruent mod the stride, or (B) some phase offset at which every block start is a token boundary.  Over **2,026 unrolled loops in 8,643 records both hold, with one stride-5 false positive** (`m/MS001E` r00) -- a real result, and worth knowing.  But a mutation test settles what it is worth as a *detector*: re-run against an opcode table with `0x152`-`0x155` deliberately regressed and **the output is byte for byte identical**.  The reason is that the bad walk is periodic too -- it drifts 29 bytes into a 25-byte block once and then settles, so it stays congruent, merely out of phase.  `m/MS00DB` r28 was found by reading the record and noticing the loop counters `16 15 14 13 12 11` being tokenised as opcodes `0x15 0x14 0x13 0x12 0x11`, and no automated invariant tried so far replaces that.  Weaker rules were also tried and are worse: a shared n-gram at constant stride alone flags 3,335 coincidental prose repeats, and allowing the varying bytes to move adds 27 more, all of them a loop's last period running off the end.

- **What the model actually costs the patch, end to end (2026-09-06).**  Identity build: **844 of 844 files byte-identical**.  English build: 200 files changed, 16,991 spans in 1,711 records, 7,676 branch displacements relocated; 84 edits skipped because a branch lands inside the span; `audit` checks 24,521 displacements and reports **one** finding, the known `m/MS006A` c0 r00 record-size overflow (33,637 bytes against the loader's 32,767 cap).  But the byte-rebuild is not the shipping path -- the overlay is, and **the overlay refuses 0 rows**: 298 files, 17,174 spans, and the worst container in the game (`m/MS006A` c0, 5,891 bytes of virtual tail) uses **16% of its room**.  So the record-size cap costs the shipped patch nothing.  **The claim that the 84 branched-into spans also cost nothing was wrong, and it was the expensive kind of wrong** -- see the entry below.  Coverage lost to the model is **0.72% of the game's Japanese**: 1,571 characters in 67 rows whose record does not tile, plus 1,492 in 318 other `@noedit` rows, out of 424,940.

- **The 24 branch misses, run down (2026-09-06).** 16 distinct sites; `m/MS6F00` and `m/MS6F1F` are byte-identical.
  - **Six are not independent findings**: `m/MS6F00` r02, r06, r08, r13, r22, r24 sit in records that do **not** tile, so the miss is a symptom of a desync further up the same record.
  - **Eight are real**: `m/MS610D` rF1, rF4, rF5, r26, r34, r5A and `m/MS6200` r14, r56 all tile cleanly, use no unimplemented opcode and carry no top-level bad selector -- yet a branch lands off a boundary. `m/MS610D` rF4 is the worked case: `1F0D` claims the expression `1f e5 0c e5 e5`, but `1F E5` is a real opcode (691 uses, no operands) and the branch points at exactly where the token would end had the expression stopped at `1f e5`.
  - **Two hypotheses were tested and disproved.** (a) *These opcodes measure the displacement from the end of the token rather than the end of the rel16 field.* Only opcodes with operands **after** the rel16 can tell the two apart, and across those: end-of-rel16 lands 16,501 of 16,517, end-of-token 2,690 of 15,766. The current base is right; `1F08`'s apparent "+4 fits perfectly" was n=4. (b) *Expression kind `0x0D` reads its nested expression conditionally, like `1E C4`.* It does not -- `0x00438C40` is `call READ_U8; call EXPR_DEREF` with the dispatch **after** both, no mode flag.
- **"Garbage" is the wrong word, and it has been used carelessly in this repo (including by me, in several commit messages).** A row whose text reads as nonsense is not evidence that the bytes are nonsense -- the game shipped and runs on them. The only claim the evidence supports is **our tokenizer put a text span where the bytes are not text**, which is a statement about the model. Three things make that the honest reading:
  - Two were already proven meaningful this session. `1FA7`'s id table holds the same values the neighbouring `1F60 00 XX` opcodes take, and `m/MS7F05`'s "dictionary" is reached only through the unclaimed tail bytes of `1E BE`.
  - **48 of the 50 rows still left blank sit in records that tile *cleanly*** -- the walk consumes them end to end and lands on the terminator. Passing the tiling check therefore does **not** mean the parse is right; it means the walk did not fall off the end. `ok` counts records, not correctness.
  - The bytes are structured. `m/MS6200` rB2 ends `11 0a 0f 00 00 | e4 b3 | 01 00 | e4 bc | ff 00` -- regular two-byte groups closed by `ff`, the same shape as the FF-terminated lists already found behind `0x103`/`0x104` and still open behind `1FA7`. `e4 b3` and `e4 bc` decode to 莎 and 莨, obscure kanji no script would use; `ff` is not valid cp932 at all.
- **The model is not complete, and the numbers say by how much.** Of 768 opcodes, **269 are not implemented** and 105 more are modelled as consuming nothing because the static tracer took the fall-through. 74 records do not tile, 93 use an unimplemented opcode, 43 carry an expression selector the engine would refuse, 1,099 end somewhere other than their terminator, and 24 branch targets do not land on a boundary. Every "garbled" row is downstream of one of those gaps, so the right expectation is that they are **recoverable**: a model fix turns them into either operands (and they leave the tables entirely) or real text (and become translatable). None of them should be treated as permanently unreadable.
- **Engine boundary agreement was measuring the wrong denominator; the opcode model now has *zero* known disagreements on the traced routes.** `1F01` prints a party-member name by reading it through the same byte fetch the tracer hooks, but out of a *string buffer*: the PC restarts at 0 and counts up in twos, one event per character, then execution resumes just past the `1F01` token. Verified end to end at `m/MS0017` r02 0x9E (`1f 01 00 00 04 ff`, four events spelling 葛城史人, resume at 0xA6) and across all 74 runs: every pc is even and ≤ 8, every character decodes as cp932, and the strings are 葛城史人 / 橘由宇香 / a counter. **No record holds those addresses**, so scoring them against our tokenisation said nothing about the model -- and it is the whole reason the figure sat at 98.4%. `giten/trace/core.py` now classifies them (`NAME_KIND`), strictly: a `1F01` token must sit on one side of the run, the body must be even PCs ascending from 2 that decode, and execution must resume inside a record. Of 18,683 events on `jp2` + `jp-friends`: 252 name-buffer, **0 model errors**, 29 script-end (a v1 tracer limitation -- it read the context after `exec_token` returned and the engine had already cleared it; v2's `pc0` fixes it, but no v2 trace has ever been captured), and 10 excursions no `1F01` bounds, left as disagreements because their cause is unproven (`m/MS00D8` r00; the token before them is `1F86`, which is `push $1; push $1; call 0x00434740` -- a conditional branch, so it cannot be the printer, and the RECID logged there is stale). **So "pull on the opcode model to raise agreement" is finished work: the ceiling it can reach is the number it is already at.**
- A decoder bug found in the same pass: `locate` rule 1 accepted *any* text token ending at the logged pc without checking the character, which shadowed rule 2 (a branch landing on that pc). At `m/MS7F04` r07 0x2A the engine had jumped onto the `18` opcode starting there and the two text bytes ending there were charged with the disagreement. Those were the last 3 "model" errors and they were never the model.
- **`1E C4` reads one expression, not two** (fixed 2026-09-06). Found with no trace and no playing: of 25,346 rel16 targets corpus-wide, 25 do not land on a token boundary, and one of those is in `m/MS00D8` r05 -- a record the engine executed 187 times on the traced routes. `1E C4`'s trampoline is `push $1; call 0x00433860`, which forwards to `0x004335E0`: that reads two u8 (`0x004335A0`), then calls `0x004335C0`, which reads an expression **only when its argument is 0**, then always reads one more. Mode 1 therefore takes `u8 u8 expr` = 6 bytes, and 0x25 + 6 = 0x2B is exactly the branch target that missed. Its sibling `1E C3` is the same shape with mode **0** and does read both, so the table was right for it -- that pairing is the control. Same family as the `0x14C`-`0x151` fix, missed because it reaches `0x004335E0` through an extra hop. `ok`/`stray`/`unimpl`/`untiled`/`impossible` all unchanged; engine boundary agreement 98.40% -> 98.43% on `jp2`/`jp-friends`.
- **`tools/opcode_operands.py` reports operand *counts*, never order.** `spec()` emits `["u8"]*a + ["u16"]*b + ["u32"]*u + ["expr"]*c`, so any opcode whose real layout is not u8s-then-u16s-then-exprs is printed as a mismatch. `0x00B` is the worked example: the tool says `u8,u8,u16` against the table's `rel16,u8,u8` and looks like a bug, but `0x00430008` is `push $1; push $0; call 0x00434850`, whose first call `0x00434680` is `jmp 0x00433EC0` -- the rel16 reader -- before `0x00434780` reads the pair. The table is right. The corpus says so too: with the displacement in the first slot 1,263 of 1,267 targets land, with it last only 46 of 96 do and 1,174 fall out of the record entirely.
- **Two disproven hypotheses, recorded so they are not re-tried.** (a) *`1F0D`/`1F0E` take no operand.* The bytes look like it -- `1f 0d 1f e5` reads naturally as two opcodes, and it moves `untiled` 74 -> 38 -- but the handler walk says both read an expression, and `impossible`, the counter that cannot improve by accident, gets **worse** (43 -> 50). Rejected. (b) *Expression selector `0x02` is a u16.* It scores better on the branch oracle (25 misses -> 13), but selector `0x02`'s handler `0x00436B3B` calls `0x00438FE0`, which is `0x00438EC0` = two u16 fetches with the second shifted left 16, i.e. a real u32. The gain is an accident: `0x02` occurs 13 times in the whole corpus, 12 of them in `m/MS6F00`/`m/MS6F1F` (byte-identical duplicates), and 10 of the 12 "fixed" misses are in records that never tiled. A rare selector shortened by two bytes reshuffles boundaries in already-broken records. **The branch-landing oracle can flatter exactly like `stray` and `overrun`; check whether the records it fixes were sound to begin with.**
- **The other 24 boundary misses are in records nothing has ever executed.** `m/MS610D`, `m/MS6200`, `m/MS6F00`, `m/MS6F1F` contribute 0 traced events between them, and `m/MS6F00`/`m/MS6F1F` are byte-identical, so 25 sites are 17 distinct and 16 of those are unexecuted. Whether they are code the routes never reach or data tokenised as code is open; the `1E C4` result shows the branch oracle can settle such a case when the record is real code, and the `0x02` result shows it cannot be trusted alone when the record is not.
- **The tag-`00` spans that reach the `japanese` rule are data, not text -- but not one kind of data.** Two were run down on 2026-09-06 and neither is "garbage" in the sense of meaningless bytes:
  - `m/MS0007` r35 and its siblings (`ｮｭｱｲｳ`, one half-width kana per span): `1FA7` at 0x0192 is typed `rel16 + expr + expr` and consumes 8 bytes, but the site is `1f a7 | 91 01 | 00 b0 00 af 00 ae 00 ad 00 b1 00 b2 00 b3 | 04 ff` -- a **variable-length list**, of which the model claims the first two entries and the other five become NUL-opcodes and one-byte "text". The values `b0 af ae ad b1 b2` are the same ids the neighbouring `1F60 00 XX` opcodes take, so they are operands beyond doubt. Same shape as the `0x103`/`0x104` fix (a list where the table claimed a fixed count).
  - ~~`m/MS001F` r02: 11 bytes sit between two `1E BE` tokens and nothing claims them.~~  **CLOSED 2026-09-07: `1EBE` reads a different number of operands depending on its own first byte.**  Handler `0x0043161A` -> `0x004324B0`: `u8 mode`; if non-zero, `0x004335A0` reads two more u8 (the 3 bytes the table had); if **zero**, `0x00437490` is called six times -- six expressions.  The static walker followed the `jne`-not-taken arm and never the other, which is the documented fall-through failure mode, and here it was not harmless: **131 of the 262 `1EBE` sites in the corpus have mode 0**, across 39 files.  Each one made the walk resume early, so every token after it in that record was at the wrong offset.  Measured against the tables we ship: **442 spans of English written over bytes that were never text, and 2,868 more at the wrong address.**  The eleven bytes this entry could not account for are exactly the tail of the six-expression form -- the fix was derived from the handler, not fitted to the record, and it explains it anyway.  Pinned by `test_1ebe_reads_six_expressions_when_its_mode_byte_is_zero`.  Corpus effect: 722,723 -> 721,670 tokens, 44,473 -> 44,031 spans, untiled 73 unchanged, branch landing 99.413% unchanged.
  - **Why nothing caught this.**  Extraction and build use the same tokenizer, so `stale_rows` matched and `audit` agreed with itself.  A checker that re-parses both sides with the model cannot see an error *in* the model.  That is the blind spot, and it is architecture-independent: the byte build had it too.
  - **The rest of the queue (swept 2026-09-07).**  Every implemented, used opcode's handler was walked for the same shape -- a branch whose arms read different amounts.  49 of 384 flagged, of which the switch-table kind byte (14 opcodes, `0x4327D5`), the `0x4335E0` family (16, `0x4335C6`), `1E10` (`rule:wait_1E10`) and `1EBE` are already modelled. **Genuinely unmodelled and worth the same treatment, biggest first:** **all of it was walked by hand the same day, and only one was a real bug.**  `0x434759` (12 opcodes, 2,022 uses, the `1F8x` family) is a FALSE POSITIVE: the gate is `[esp+0x10]`, a caller-pushed constant, not stream data -- every handler is `push <gate>; push <n>; call 0x434740`, and the six that push 1 are exactly the six typed `rel16,expr,expr`.  `0x42FEE5` (`1F03`/`1F04`, 911) is `pairs_ff`, already fixed earlier; `0x435D06` (`1E1E`, 609) calls the menu rescanner `0x435CF0`, which is `list_ff`; `1F8B`-`1F8F` read `rel16` then only game state.  All correct.  **The one real bug was `0x43563B` (`1FA7`/`1FA8`, 5 uses)** -- worker `0x00435620` loops on `0x00437490` until a value is `0xFFFF`, so it is `rel16` + a `-1`-terminated expression LIST, not `rel16,expr,expr`.  Fixed: `expr_list`, and the five sites now consume 18-32 bytes instead of 8.  That closes the `ｮｭｱｲｳ` rows above -- they were the stranded list entries.  **The sweep's own lesson: it cannot tell a branch on stream data from a branch on a caller constant, so its output is candidates, not findings.**  Pinned by `test_1fa7_reads_expressions_until_one_is_minus_one`.

## overlay (runtime translation)
- **What v6 does not know (2026-09-10).**  The overlay identifies no file.  A translated span is keyed on the content of the record it lives in -- `(record id, record length, FNV-1a of the record's bytes)` -- and the hook finds the record the program counter is in from the buffer's own index, hashes it, and looks that triple up.  Three things follow, and they are the whole list of what the design cannot do:
  1. **Two files holding a byte-identical record must carry identical English.**  One key, one translation, by construction.  254 record keys in `tables/` disagreed the day v6 was written -- "Man:" against "Male:", three renderings of "There's no one here..." -- and `tools/unify_duplicates.py` resolved them in the tables.  `giten check` reports any new one as an `overlay-conflict` **error** and `giten overlay` refuses to build, so this cannot drift back silently.
  2. **A record the engine mutates at run time draws Japanese.**  Its bytes are not the bytes we translated, so its key is one we do not hold, and a key we do not hold is served nothing.  The measured case is record `0x97` of a demon merge: 976 bytes at run time against 82 on disk.  This is a coverage loss and never a wrong address -- which is the whole trade content addressing makes.
  3. **Text the interpreter does not fetch is not the overlay's to serve.**  `et/ID*` tables, the item and skill databases, the exe's own menu strings and the `p/` name fields are read by other code paths; they are patched directly and bounded by their own rules.
- Spans are diverted only when entered at their first byte; a branch landing inside a translated span shows the Japanese tail (same 115 lines `@noedit` blocks).  **This was written as a description and was not true until 2026-09-07**: the hook answered *every* address inside a span, so a branch aimed at the line's own trailing `1E 10` page wait got a letter of English and the interpreter ran prose as opcodes.  278 such addresses shipped, across 75 files.  `SpanEntry.served` now stops the served run at the lowest branch target inside the span and `overlay.dat` stores that length rather than deriving it, so the sentence above is enforced by `test_the_overlay_never_answers_an_address_a_branch_jumps_to`.  It cost no coverage: the capped bytes move into the virtual tail, so a sequential read still shows the whole line.
- **Per record, the English excess over the Japanese must fit above the image end.**  `tail_total <= 0x10000 - MAX_IMAGE_END`, where `MAX_IMAGE_END` (0xA000) over-estimates the highest image end any buffer that can hold one of our records reaches -- measured over every `m/` container (worst `m/MS0030` c0 at 0x8EA2) and every `et/ET0007` merge (worst 0x34D3), and re-measured by `test_max_image_end_still_bounds_every_buffer_one_of_our_records_can_be_in`.  The worst record in the draft tree spends 7,422 of the 24,576 bytes it may.  This replaced a per-**file** bound: a record's tails are laid out from its own image end and the record can turn up in any buffer, so the bound has to hold for the worst one.
- **A virtual program counter is resolved through the per-handle memo, and the memo can be lost.**  Every record's tails begin at the same `image_end`, so a virtual address names no record on its own; the hook answers it from the record the previous fetch on that handle was in.  Sound because no opcode the codec may embed in a span transfers control within one handle (`codec.INLINE_OPS` is the newline, the page wait and the eight pool calls, and a pool call switches buffers).  But two handles congruent mod 16 share a memo slot, and two contexts pointing at one buffer thrash it -- either would leave a pending virtual address unresolvable, and the hook returns `0xFF` there rather than reading memory it does not own.  Not observed; stated because it is the one piece of state v6 still keeps.
- **A memo could in principle survive a buffer swap it should not.**  Validity is handle, base pointer, the buffer's own index entry for the memoised record, **and** the program counter the last fetch handed back.  The fourth is load-bearing and was not in the plan: 92 `(record id, offset, length)` slots in the corpus hold more than one record -- 257 records in all, 80 of the slots holding something we translate, `rec 00` at 0x400 length 9 being seventeen different records -- so the first three can all pass over a reload.  The program counter closes it because a script load sets a new one.  What would still get through is a reload that leaves the buffer at the same address, presents the same record id at the same offset and length with different bytes, *and* resumes at exactly the program counter the hook last handed out.  A script load does not do that.
- **`giten overlay` refuses to write anything while an `overlay-conflict` stands.**  Not a warning: two files that disagree about one record would hand one of them the other's line, which is the class of bug v6 exists to remove.
- `et/ID*` tables are read by other code paths, not the interpreter fetch; the hook does not cover them.
- **SUPERSEDED (2026-09-10): "the whole `m/MS6xxx` family is never served".**  That entry described `rebind()` failing to identify a demon-conversation buffer, because the engine reports those as file ids `0xE0..0xEF` that no filename maps to and their index is a merge of up to five files that cannot be computed statically (record `0x97` is runtime-sized).  Both halves are still true about the *buffer*; they are no longer true about the overlay, because v6 does not identify buffers.  The merge moves a record, the live index says where it went, the record's bytes are unchanged, so the key matches and the English is served.  A record another file replaced is different bytes, so it is a different key, and nothing else in the file is affected.  `tests/test_negotiation_image.py` keeps the measurement and now also asserts the answer.
- **The opcode model has no known defect anywhere in the corpus (2026-09-08).**  All 73 untiled records are accounted for and none is a tokenizer error: 2 are dead data after a terminator, 3 spill past their record (one of which, `m/MS0031` r02, crashes the real game), 1 is the corpus's only unterminated `pairs_ff`, and 67 are in files with no loader found.  Verified four ways -- handler walks against engine code, the expression table 94/94 against the engine's own two tables, corpus consistency, and the engine's own program counter (946 observed token starts, 943 matching, 2 a startup artifact, 1 the predicted spill, **0 unexplained**).  **Full write-up and the limits that qualify it: `docs/opcode-model.md`.**
- **No loader has been found for 16 of the 46 `m/MS6xxx` files, and they hold every untiled record in the family (2026-09-08).**  Stated as "no path found", *not* "proven unreachable" -- see the caveats at the end of this entry.  The negotiation merge is the only thing that names an `m/MS61xx` file, and it forms the id in one instruction (`0x0040EC31 add $0x6100,%edx`, from `table[id*3+2]`, kind 9).  The table is read, not inferred: `0x0040EB70` lazily loads **`et/ET0007.BIN`** itself (`push $0x7; push $0xc; call 0x401dd0`) and caches the pointer at `0x47B4F8`, which nothing else writes.  Its third column is `{00,06,07,08,09,0B,0C}` and **never `0D`**, so `m/MS610D` -- 40 untiled records, long filed as "loader unknown" -- is simply unreachable, along with `MS6101`-`MS6105`, `MS610A`, `MS6200`, `MS6300`, `MS6400`, `MS6500`, `MS6800`-`MS6802`, `MS6F00`, `MS6F1F`.  Ruled out alongside: no `0x610D` immediate exists in the code range (191 raw hits, 0 in code); only one call site of the merge (`0x0040E9CA`); the two other `et/` files sharing the table's shape name 22 and 9 files that do not exist; and **no script opcode can pass a u16 file id** -- every file-referencing opcode hardcodes a pool (`m/MS7F0x`) or takes a u8 resolving to `m/MS00xx`. That is the wrong way round, and it cost the untiled-record work weeks.  `0x00433D70` -- goto-record, the function the `0C` handler already calls -- takes the file id in a **u16**: `cmp di,0xde` at `0x00433D82` compares the whole word, the id reaches `0x00433CA0` -> `0x0043B720` as a `u16` key into the loaded-buffer list at `ds:0x00481688`, and a miss goes `0x0043B650` -> `0x0043AD20` -> `0x00401DD0(id, kind 9, 0)`, i.e. the generic `m\ms%.4x.bin` path with the id stamped back into the buffer at `mov [edi],bx`.  So **any** `m/MS*.BIN` can be loaded and run; what no shipped code does is *form* the ids `0x6200`, `0x6500`, `0x6F00`, `0x6F1F` and hand them over.  Two consequences. ## trace / verify
- **`verify` needs a v4 trace or better, and asks nothing about files.**  Overlay v6 keys a translated span on the content of its record, so the oracle has to carry that content: `trace.S` logs `rec_hash` (FNV-1a over the record the interpreter is standing in) and `image_end` (`idx[255].off + idx[255].len`).  `verify` looks `(rec, idx_len, rec_hash)` up exactly as the hook does, reconstructs the bytes the engine was handed at `pc0` -- from the served English where the overlay answers that address, from the original record where it does not -- and demands they equal what was logged.  A trace older than v4 is **refused**, not guessed at.
- **Until v5 the oracle named the record from `ds:RECID` and the hook named it from the program counter, and that gap was never checked.**  `hook.c`'s `find_record` searches the live index for the record containing the pc; `trace.S` read the engine global instead, which is written on *load*.  The sentence this entry replaces -- "a record is named by its bytes, so a stale `0x4911B0` cannot misdirect a single address" -- was **false**, because `trace.S:137` read `0x4911B2` and the bytes it then hashed were whatever that named.  Measured on the 2026-09-11 Roppongi session: 165 findings that were not findings, 450 events called unverified, and 611 served events charged to the wrong record -- all of them the Alice scene of `m/MS0032` c0, pc in record `0x22`, RECID still saying `0x59`.  v5 scans the index the way the hook does and logs which answer it gave (`REC_FROM_PC`).  The stale-label gate, the overlay-pairing gate and the container-0 limitation are still gone, and `decode`, `diff`, `bases` and `files` still use the *file* label -- they are about the Japanese build, where the label is all there is.
- **Two tracer categories, neither of them a finding.**  (1) *record does not contain pc0*: the record the trace names does not hold `pc0 - 1`, and the trace does not claim to have found it from the program counter.  Nothing about the address can be concluded in either direction, so it is counted and reported, never charged to the overlay; on a v4 trace this is where the 614 Roppongi events above land.  (2) A **VIRTUAL** event -- `pc0` at or above the image end -- logs no record at all, because every record's tails begin there, and is attributed offline to the record the same buffer `handle` was last in, the same resolution the hook's memo does at run time.  An address that is still unplaceable *after* that, on a record the trace says it found from the pc, remains the 2026-09-07 soft-lock finding.
- **`pc0 >= image_end`, not `pc0 - 1 >= image_end`, is what makes a program counter virtual.**  The byte was fetched at `pc0 - 1` only when the counter advanced by one, and the handoff that hands it to a record's *first* virtual tail lands on `image_end` exactly (the first tail of a record has `virt_off` 0).  2,429 of the Roppongi session's events sit there; scanning for `image_end - 1` would attribute every one of them to whichever record happens to end the buffer.
- **A record's file and record ids are engine globals written on *load*, not on every context switch, so they go stale.** `0x4911B0`/`0x4911B2` name the script most recently loaded; the interpreter runs whichever buffer its context points at, and several are resident at once. This is what produced the retracted "228 program counters outside the file" finding: the index entry logged was `(0x4BEF, 1)` and `m/MS00DD`'s whole index stops at `0x1CC9`, so the buffer executing was never `m/MS00DD`. It is still true of the label, and of `rec` on any trace older than v5 or on a v5 event whose scan found nothing; it is no longer true of anything the hook does with it.
- **A record no file on disk holds is counted, not judged.** The loader builds some at run time -- record `0x97` of a demon merge is 976 bytes against 82 on disk -- so `corpus_records()` has no bytes for it and nothing is claimed.
- **`pc0` is one past the token's first byte, not the token's address.** The caller fetches that byte (two, for a wide character) and the fetch is what advances the PC; an opcode's operands are consumed later, inside the handler. Measured on the soft-lock trace, restricted to addresses the overlay does not serve: 35,713 events carry the logged character at `pc0 - width` and **none** carries it at `pc0`.
- **Two fetches do not advance the program counter by one, and `verify` has to know both.** The last byte of a span's English hands it to the span's end; the last byte that fits in place hands it to the tail's virtual address. So an event logged at one of those program counters had its bytes read at the address that handed it over -- and a wide character can straddle such a handoff, lead byte in place and trail byte in the tail. Without both cases a clean run reports findings.
- **After a pool call (`01`-`08`) the logged `pc` is an address in the *pool* file.** Our own spans contain those opcodes wherever a word comes out of the dictionary, so the byte reconstruction keys on `pc0`; keying on `pc` produced a run of "byte does not match the original" findings against text that was ours and correct.
- **One unexplained record per trace: `#0`, `m/MS002D` rec `0x00`, `pc0 0x0401`, `ch 0xFE18`.** The byte at that address is `1E`, the token is the 6-byte `1e fb 00 00 03 ff`, and the low half of the logged character (`0x18`) matches neither. It is always the first record of the file and always identical, so it is a startup artifact of either the engine or the hook; it has never been chased down.
