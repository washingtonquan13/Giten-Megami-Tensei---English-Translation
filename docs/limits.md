# What the tooling does not know

Every re-adopted module carries an entry here.  An entry is closed only by evidence from the exe or the tracer, never by a plausible theory.

## container / records
- **A record may not exceed 32,767 bytes** (closed 2026-09-04 by the tracer + disassembly of the loader `0x43ABC0`: the per-record growth delta is a signed 16-bit value; over 0x7FFF it goes negative, the shrink path runs and the game crashes on load).  The original's largest record is `m/MS006A` r00 at 28,291 bytes -- the BBS -- so English there has 4,476 bytes of headroom.  Enforced by `check` (`record-size`, predicted from the tables) and `audit` (measured on the build).
- Record-count words that overstate the body (`m/MS600A`, `m/MS610B`, `et/ID00A2`, `et/ID00A3`) and trailing bytes are copied verbatim; what the engine does with them is unknown.
- Containers with duplicate record ids and branches (`m/MS6000` c0/1/8, `m/MS6800` c0, `m/MS610B` c15) are not editable.

## vmops / opcodes.json
- 267 opcodes are typed as consuming no operands because the static tracer took the fall-through; 148 records cannot be tiled (123 before the switch grammar; the 25 newly refused ones tiled by luck and were editable).  `1F82` is a known offender: its operand model eats the next opcode's `1F` prefix (`m/MS0002` r26, `m/MS0015` r02, `m/MS0032` r22).
- ~~`1F01 nn` followed by `00`: meaning unknown.~~ **Closed 2026-09-04 by trace:** `1F01 nn` prints runtime string *nn* -- `00` is the player's name (the trace shows the PC jump to offset 0 of the name buffer and read 葛城史人), other indices print counters (`６`). The `00` after it is that string's terminator. v0.05 stripped all 3,240 and hard-coded names; we keep them.
- ~~The byte after a name macro in the post-menu dead zone (`00 02 01 6a`): meaning unknown.~~ **Closed 2026-09-04:** those bytes are a switch-table case (`[case 02][kind 01][rel16]`, format-notes 2.12) that the old five-byte model for `0F` had spilled into the text.  They are operands now and never reach a table.
- Switch tables (`0E`/`0F` and 14 relatives) are decoded from the handler; a `kind` byte other than 0/1 refuses the record.  Which records those are is known (25 that used to tile by luck), what their real layout is, is not.
- `NOT_A_BRANCH = {010, 011, 182}` is statistical (target lands on an instruction at or below chance).  `017` is in the grey zone on the original (48.7% vs chance 43%) and is still relocated.
- ~~Our expression model disagrees with the engine for 67 of 94 selectors.~~ **Closed 2026-09-06: it does not.  The extraction was wrong, twice over.**  `tools/extract_expr_nodes.py` carried its own control-flow walker which, on a `call`, compared the target against the readers it knew and otherwise stepped *over* it — so every kind handler that reads through a helper reported "consumes nothing".  Kind `0x0D` (selectors `19`–`23`) is the proof: `0x00436C49` calls `0x00438C40`, which is `call READ_U8; call READ_EXPR_DEREF`, i.e. `u8 + expr` — exactly what `opcodes.json` already said.  Separately, **there is a third stream reader, `0x00438FE0` (4 bytes, fetcher `0x438EC0`)**, alongside `0x00438FA0` (1, `0x438E50`) and `0x00438FC0` (2, `0x438E80`); not knowing it made selector `0x02` look like a leaf when it is a `u32`.  Following delegation and counting all three readers, the engine agrees with `opcodes.json` for **94 of 94 selectors** (see the next entry for the last two).  The extractor now reuses `tools/opcode_operands.py`'s walker instead of keeping a second one that could drift.
- ~~Selectors `0x4B` and `0x4F` are context-dependent in the engine.~~ **Closed 2026-09-06: they are not, and the expression model is complete at 94/94.**  A third walker bug: an indirect `jmp *0xTABLE(,%reg,4)` was followed as if the table address were a code target, so it decoded jump-table *data* into paths that consumed bytes nothing consumes.  Their callees (`0x00437440`, `0x004373E0`) are `movswl 0x4(%esp); cmp $3; jmp *table` — a dispatch on the value the caller already read, taking **nothing** from the script stream.  Both selectors are one `expr`, as `opcodes.json` said.  The walker now reads the jump table out of the image and follows every entry.
- ~~`tools/opcode_operands.py`'s `_at()` is order-dependent~~ **Fixed 2026-09-06.**  It answered from any previously-cached 0x200-byte linear sweep containing the address, but a sweep runs off the end of small functions into padding and drifts, so the answer depended on what had been walked first — selector `0x59` read as a leaf in a full run and as `u8 + expr` when walked first in a fresh process.  It now decodes from the nearest *proven* instruction boundary, and boundaries are recorded as control flow proves them.  Three walker bugs were found in one day (step-over-calls, cache order, indirect-jump targets); treat a surprising result from it as suspect until the disassembly is read.
- The expression table was **not** what blocks the untiled records, and neither is the switch grammar.
- **Switch tables are fully statically determinable: a table is always `4N + 1` bytes** (verified 2026-09-06 from `0x004327C0`).  `cmpw $0x0,0x14(%esp); je 0x432845` is *not* an early-out — it selects a second, parallel loop with the **identical** byte layout, differing only in the match test: mode `0` takes the first case whose key is `>=` the selector (cumulative threshold, right for `0E`'s 1..100 roll), mode `1` takes exact equality (right for `0F`'s menu byte).  Neither mode skips the table, and neither early-exits on a match, so the PC afterwards is always `table_start + 4N + 1`.  The mode is a literal `push` immediate at all nine trampolines and is never computed, and it does not affect length, so a tokenizer never needs to know it.  Case layout `[u8 key][u8 kind][u16 payload]`, `kind == 0` → `[u8 file][u8 rec]` via `0x00433C10` (two `READ_U8`, branchless), else rel16 via `0x00433EC0` (one `READ_U16`; it also confirms `rel16_target = pc_after_operand + imm16` directly).  `vmops._read_switch` was already correct.
- `_read_switch` refuses `kind > 1`.  That is **not** VM-faithful — the handler only tests `kind != 0` — but the compiler emitted only 0 and 1, and every record the guard rejects proves to be desynced anyway (kinds 16/174/240/227, non-ascending keys).  It is kept deliberately as a desync detector: dropping it converts loud failures into silent mistilings.
- The 26 remaining switch failures are **runaway walks with an upstream cause**, not switch-decoding problems.  Clean tables average 2.4 cases with 98.8% of kinds in {0,1} and 99.1% ascending keys; the failing ones average 40.4 cases, 21.1%, and 8.0% — they are random record bytes.  All 52 belong to `0x00E`/`0x00F`, single-byte opcodes with no pre-operands, so the table's start cannot be mis-modelled: the walk arrived at a byte that was never an opcode.  Corroboration that the 4-byte stride is right: of 5,365 rel16 fields inside cleanly-walked tables, 99.22% land on a legal instruction boundary, better than ordinary branch rel16s (98.52%, n=19,956).
- **Opcode `10` vs `1F 00` (2026-09-06; superseded later the same day -- the headline was backwards, see the dispatcher entries below).** `10` was the loudest lead -- 26 of its 55 expressions impossible, and in `NOT_A_BRANCH` on statistical grounds -- but it is exonerated. Its dispatch entry reads exactly what the table says (one u16, one expr, `reads()` = `(0,1,0,1)`), which is **identical to `12`**, whose branches land 254 of 256. What separates them is what comes before: **42 of the 55 `10`s sit immediately after `1F 00`, and every one of the 16 testable misses is in that group.** Not one `10` following a known opcode misses. Resolved against the whole container image (records are contiguous at runtime, so a within-record test undercounts): `10` lands 15/55, `11` 8/59 -- read at the time as "not branches", which the disassembly later contradicts: `0x00433C40` writes the PC, so they are branches whose rel16 we are reading from mis-framed bytes. The same run clears a standing doubt: **`17` lands 62/62 against the image**, so the "grey zone, 48.7% vs chance 43%" note above is resolved in favour of relocating it.
- **`1F 00` is settled: it is exactly a two-byte no-op (2026-09-06, from the dispatcher).**  `0x0042FF50` is the opcode dispatcher -- the image's *only* reference to the table at `0x004318B0` -- and it indexes that table by the raw token value under `cmp $0x2fd; ja 0x4318aa`.  Table entries `1D`, `1E` and `1F` are the three escape prefixes: each reads **one** byte, adds `0x300`/`0x200`/`0x100`, re-checks the same `0x2FD` bound and re-dispatches.  So `1F nn` is index `0x100+nn` and two bytes; `1E nn` is `0x200+nn`; and `1D nn` is always past the bound, i.e. "eat one byte, do nothing".  `handler(0x100)` is `0x004318AA`, `xor ax,ax; pop esi; ret`.  The fetch path was then walked to the bottom and holds nothing extra: loop `0x00439090` -> `0x00439000` (pushback `0x00453BC0`, else `0x00438F50`) -> `0x00438F00`, which reads one byte and takes a second **only** when the `_ismbblead` bit `0x04` is set in the locale table at `0x00490C11` -> `0x00438E50`, a plain `[base + pc++]`.  There is nowhere for an unexplained byte to go.  The earlier note's other candidate, "`exec_token` handling `1F 00` before dispatching", is disproved: `exec_token` (`0x00439020`) receives an already-assembled token and fetches nothing itself.
- **The open question is opcode `10`, and `10` *is* a branch.**  `0x00430055` (`10`) and `0x0043007B` (`12`) are two of fourteen handlers at a 0x13-byte stride covering opcodes `0B`-`18`; each is `push c; push b; push a; call 0x004348B0` and they differ only in the three immediates.  `0x004348B0` reads, in this order, `0x00434680` -> `0x00433EC0` (`read_u16(); target = PC + imm`) and then `0x00437490` (`read_expr(); deref`), and finishes with `0x00433EF0(target, cond)`, which for `cond == 0` calls `0x00433C40(target)` -- and `0x00433C40` is literally `mov ecx,[0x00491160]; mov ax,[esp+4]; mov [ecx+0x0e],ax`, i.e. **write the PC**.  The family is `if !cond goto PC+rel16`.  So `['u16','expr']` is the right operand list *and the right order*, and `NOT_A_BRANCH` for `10`/`11` is wrong as a claim about the engine; it survives only as a tiling heuristic.  Corollary: the branch-landing measurement above is circular for `10` -- the rel16 it tests is read from bytes whose framing is what is in doubt.
- **What actually breaks, restated correctly.**  It is not four bytes and it is not `1F 00`; it is one character at the `10` sites that follow `1F 00` (42 of 55).  Three shapes, and no single reading of `10` fits all three:

      `10 01 00 0f` x7   ours resumes `ん、健康...`      the text is `うん、健康...` at +4
      `10 01 01 82` x8   ours resumes `｢きなり、倒...`   the text is `いきなり、倒...` at +3
      `10 01 01 1f` x23  ours resumes at `ba` (`ｺ突然...`)  the text needs `1F BA` at +3

  At the `0f` sites +4 *is* the branch target (rel16 = 1), so "the engine takes the branch" would explain them; at the `01 01` sites the target is 260 bytes away, so neither path prints what is written there.  Against our framing everywhere: the branch decision at the `0f` sites would be read from **uninitialised stack** -- the expression value is `0xA482`, `0x004374A0` returns immediately for anything above `0x0E` without writing either out-param, and `0x004348B0` reserves both with a bare `sub $0x8,%esp`.  A shipped script does not decide a jump on uninitialised memory, so the engine is probably not at that PC at all.
- **The 11 `10 1f c1 00 03` sites are confirmed correct as we tile them**, by a different argument, and they are the reason not to shorten `10` globally: a three-byte reading would put the next token on `00`, and opcode `00` is `or ax,0xffff; pop esi; ret` -- the sentinel the interpreter loop tests with `test ax,ax; jge`, i.e. the record terminator.  Every one of those records would end there.  These 11 follow `07`, never `1F 00`.
- **The expression model is now proven against the engine, 94/94.**  `0x00436B00` reads a u8 selector, maps it through `0x00437380` (selector -> kind, 62 kinds) and jumps through `0x00437288` (kind -> handler); both tables are in the image, so every selector's shape is a fact.  Walking all 62 handlers reproduces `docs/opcodes.json`'s `expressions.nodes` for **all 94 selectors, with no disagreement** -- including `0x0F`, which is kind 12, handler `0x00436C33`, `call 0x00438FC0` = one `u16` (shared with `0x01` and all of `0x0D`-`0x18`).  This retires the "NOT yet trustworthy / disagreed with 67 of 94" caveat from the first pass, which was an artifact of a bad function-extent heuristic.  **Do not "fix" `10` or the expression table.**  The decisive experiment is unchanged and now sharper: one traced route through `m/MS0031`, asking only whether the engine's PC is ever equal to the offset of a `10` byte that follows `1F 00`.

- **RETRACTED: "an `expr` beginning with `1D`/`1E`/`1F` is proof of a bad parse" (2026-09-06).**  It is not.  Those three bytes are the opcode escapes *in opcode position*; the expression reader never treats them that way.  `0x00436B00` reads one raw byte and indexes the kind table at `0x00437380`, where selectors **`0x19`-`0x23` all map to kind 13**, handler `0x00436C49`, `['u8','expr']` -- so `1D` and `1E` are not distinguishable from `1C`, which the rule never objected to.  The corpus shows no anomaly either: counting the top-level selector of all 65,315 expression operands gives `19`:5 `1A`:11 `1B`:9 `1C`:14 **`1D`:13 `1E`:13 `1F`:57** `20`:8 `21`:16 `22`:29 -- `1D` and `1E` sit dead centre among their neighbours, and the rule's 83 "impossible" expressions were exactly 13+13+57, i.e. every top-level use of the three.  **Every lead it manufactured is void**: `1FE8` 34/1717, `1F53` 10/20, `1F54` 4/20, `1F0D` 3/742, `1F0E` 1/160, and -- the loudest and the one that sent the `1F 00` hunt down a false trail -- `10` at 26/55.  Pinned in the other direction now by `test_1d_1e_1f_are_ordinary_expression_selectors`.  What survives is one specific observation filed under the rule that does not depend on it: in `m/MS610D` rF4 a branch points at the byte where `1F0D`'s expression would end if it stopped after `1f e5`.  That belongs to the kind-13 question below.
- **Engine boundary agreement is 18,659 of 18,659 -- every locatable event, on every trace on disk (2026-09-06).**  Deduplicated (`jp-friends` and `jp-overlay` are the same capture; `jp2` duplicates `jp-leave`; the first trace `jp.bin` predates a fix and resolves against no build) and with the `1F01` name-buffer excursions excluded as before.  The 39 leftovers are **not model errors and not events**: the decoder's own self-check -- logged `ch` must equal the bytes at that offset -- separates them perfectly, 18,659 pass and all 39 fail.  29 of them carry `pc == 0` *and* `ch == 0`, which is no token at all; the other 10 are five repetitions of `(pc 0, ch 0x001F)` then `(pc 2, ch 0x8255)` attributed to `m/MS00D8` r06, whose first bytes are `1f ba`.  `0x8255` is the full-width digit `６`, and **no record anywhere in the game begins `82 55`**, so that `(file, rec, pc)` triple describes nothing: it is the documented stale-globals failure -- `0x004911B0`/`B2` are written only at `0x00433C7E`/`0x0043C2C8`, and a number-rendering path does not go through them.  The fix, if it is ever wanted, is the fallback already named in the plan: hook `0x00433C70` instead of trusting the globals.
- **Expression kind 13 is the one place the engine and the corpus disagree, and it is NOT applied.**  Selectors `0x19`-`0x23` reach `0x00436C49`, which calls `0x00438C40`, which is `call 0x00438FA0` (u8) then `call 0x00437490` (expression) -- both **unconditional**, with no branch between them, so the engine reads `u8 + expr` and `docs/opcodes.json` is faithful.  But 79 records refuse to tile, and every failure is a record *tail*: `1F 0D`/`1F 0E`/`1F 0F` followed by `1F E5` (whose handler `0x004314E7` is the terminator sentinel `or ax,0xffff`), always short by exactly one byte.  Measured, without changing anything: making kind 13 `['u8']` fixes **41 records and breaks 1** (`m/MS00DB` c0 r28), 38 of the fixes in `m/MS610D` and 3 in `m/MS6200`.  The independent oracle says nothing either way -- rel16 landing against the whole container image moves 92.52% -> 92.56%.  The traces cannot arbitrate: 50 tokens carrying a kind-13 expression sit in records the engine ran, and it reached the start of **none** of them.  This is the same shape as the `10` question and gets the same treatment: recorded, not "fixed".  A compensating patch that makes a counter go up while the disassembly says otherwise is how the `1F 0D` revert (`pre-expr-model`, b22272e) happened the first time.
- **The `0x004335E0` family is now complete: 22 entries, 11 per mode (2026-09-06).**  The worker reads two u8 via `0x004335A0`, then `0x004335C0` -- which reads an expression **only when its argument is 0** -- then always one more.  Every entry reaching it is `push <mode>; call <thunk>` with the mode a literal, so mode 0 is `u8 u8 expr expr` and mode 1 is `u8 u8 expr`.  `1E C4` was corrected this way, then `0x14C`-`0x151`; **`0x152`-`0x155` were missed** -- six of the ten mode-1 entries fixed, four left carrying an expression the engine never reads.  No counter noticed, because those records still *tiled*.  The witness is `m/MS00DB` c0 r28: six iterations of one block, byte for byte identical except a counter running `16 15 14 13 12 11`, **exactly 25 bytes apart**.  One iteration sums to 25 only when `0x153` is six bytes; the old model spent 29 and the walk read the loop counters themselves as opcodes `0x15 0x14 0x13 0x12 0x11`.  Found by sweeping the dispatch table for the *shape* rather than by chasing the record, and the same sweep says **no other worker+mode group disagrees** (421 groups; the single flag, `0x236` vs `0x23B`, is a false positive -- they share only `0x00438FC0`, the u16 reader itself).  Effect: rel16 landing against the whole container image 92.52% -> 92.60%, branches that could not be relocated **14 -> 5**, one more record tiles, and `m/MS00D1` gained a record that never tiled at all (+206 newly extractable rows).  Identity build stays 844/844, `audit` still reports only the `m/MS006A` cap, `check` the same 1,500 pre-existing errors.  Pinned by `test_the_0x4335e0_family_splits_cleanly_into_mode_0_and_mode_1`.
- **`0C` and `0D` are cross-record control flow: goto-record and call-record (2026-09-06).**  Both are `push <mode>; call 0x00433E70`, which reads a `[u8 file][u8 record]` pair via `0x00433C10` (two `READ_U8`, branchless -- the same reader the `0E`/`0F` switch tables use for `kind == 0`) and then branches on the mode: **`0C` (mode 0) -> `0x00433D70`, jump to that record; `0D` (mode 1) -> `0x00433E40`, which saves position via `0x0043C1F0` first and then jumps -- a call.**  `0x00433D70` carries special cases keyed on the pair (`file 0xDE record 1` becomes record 9, and others), so it is the real entry point for record dispatch.  Two consequences worth having: a record ending in `0C` ends for good, which is why 14 of `m/MS610D`'s tiling records finish on a three-byte `0C` token; and reachability inside a record cannot be decided from branches alone, because `0D` leaves and comes back.  It also means the `m/MS610D` tails after a `0D` are **reachable**, so "those bytes are dead" is not an escape from the kind-13 conflict above.
- **A record that tiles can still be tiled wrongly, and unrolled loops do NOT detect it (tried and disproved, 2026-09-06).**  `m/MS00DB` r28 tiled cleanly under a model four bytes long per iteration, and nothing in `ok`/`stray`/`unimpl`/`overrun` moved.  The obvious invariant -- a block repeated at a fixed stride must be tokenised the same way every period -- was built and run: find n-grams recurring at constant stride whose blocks differ only at the same one or two positions (a counter), then require either (A) token boundaries congruent mod the stride, or (B) some phase offset at which every block start is a token boundary.  Over **2,026 unrolled loops in 8,643 records both hold, with one stride-5 false positive** (`m/MS001E` r00) -- a real result, and worth knowing.  But a mutation test settles what it is worth as a *detector*: re-run against an opcode table with `0x152`-`0x155` deliberately regressed and **the output is byte for byte identical**.  The reason is that the bad walk is periodic too -- it drifts 29 bytes into a 25-byte block once and then settles, so it stays congruent, merely out of phase.  `m/MS00DB` r28 was found by reading the record and noticing the loop counters `16 15 14 13 12 11` being tokenised as opcodes `0x15 0x14 0x13 0x12 0x11`, and no automated invariant tried so far replaces that.  Weaker rules were also tried and are worse: a shared n-gram at constant stride alone flags 3,335 coincidental prose repeats, and allowing the varying bytes to move adds 27 more, all of them a loop's last period running off the end.

- **What the model actually costs the patch, end to end (2026-09-06).**  Identity build: **844 of 844 files byte-identical**.  English build: 200 files changed, 16,991 spans in 1,711 records, 7,676 branch displacements relocated; 84 edits skipped because a branch lands inside the span; `audit` checks 24,521 displacements and reports **one** finding, the known `m/MS006A` c0 r00 record-size overflow (33,637 bytes against the loader's 32,767 cap).  But the byte-rebuild is not the shipping path -- the overlay is, and **the overlay refuses 0 rows**: 298 files, 17,174 spans, and the worst container in the game (`m/MS006A` c0, 5,891 bytes of virtual tail) uses **16% of its room**.  So the record-size cap and the 84 branched-into spans cost the shipped patch nothing.  Coverage lost to the model is **0.72% of the game's Japanese**: 1,571 characters in 67 rows whose record does not tile, plus 1,492 in 318 other `@noedit` rows, out of 424,940.

- **The 24 branch misses, run down (2026-09-06).** 16 distinct sites; `m/MS6F00` and `m/MS6F1F` are byte-identical.
  - **Six are not independent findings**: `m/MS6F00` r02, r06, r08, r13, r22, r24 sit in records that do **not** tile, so the miss is a symptom of a desync further up the same record.
  - **Eight are real**: `m/MS610D` rF1, rF4, rF5, r26, r34, r5A and `m/MS6200` r14, r56 all tile cleanly, use no unimplemented opcode and carry no top-level bad selector -- yet a branch lands off a boundary. `m/MS610D` rF4 is the worked case: `1F0D` claims the expression `1f e5 0c e5 e5`, but `1F E5` is a real opcode (691 uses, no operands) and the branch points at exactly where the token would end had the expression stopped at `1f e5`.
  - **Two hypotheses were tested and disproved.** (a) *These opcodes measure the displacement from the end of the token rather than the end of the rel16 field.* Only opcodes with operands **after** the rel16 can tell the two apart, and across those: end-of-rel16 lands 16,501 of 16,517, end-of-token 2,690 of 15,766. The current base is right; `1F08`'s apparent "+4 fits perfectly" was n=4. (b) *Expression kind `0x0D` reads its nested expression conditionally, like `1E C4`.* It does not -- `0x00438C40` is `call READ_U8; call EXPR_DEREF` with the dispatch **after** both, no mode flag.
- **"Garbage" is the wrong word, and it has been used carelessly in this repo (including by me, in several commit messages).** A row whose text reads as nonsense is not evidence that the bytes are nonsense -- the game shipped and runs on them. The only claim the evidence supports is **our tokenizer put a text span where the bytes are not text**, which is a statement about the model. Three things make that the honest reading:
  - Two were already proven meaningful this session. `1FA7`'s id table holds the same values the neighbouring `1F60 00 XX` opcodes take, and `m/MS7F05`'s "dictionary" is reached only through the unclaimed tail bytes of `1E BE`.
  - **48 of the 50 rows still left blank sit in records that tile *cleanly*** -- the walk consumes them end to end and lands on the terminator. Passing the tiling check therefore does **not** mean the parse is right; it means the walk did not fall off the end. `ok` counts records, not correctness.
  - The bytes are structured. `m/MS6200` rB2 ends `11 0a 0f 00 00 | e4 b3 | 01 00 | e4 bc | ff 00` -- regular two-byte groups closed by `ff`, the same shape as the FF-terminated lists already found behind `0x103`/`0x104` and still open behind `1FA7`. `e4 b3` and `e4 bc` decode to 莎 and 莨, obscure kanji no script would use; `ff` is not valid cp932 at all.
- **The model is not complete, and the numbers say by how much.** Of 768 opcodes, **269 are not implemented** and 105 more are modelled as consuming nothing because the static tracer took the fall-through. 74 records do not tile, 93 use an unimplemented opcode, 43 carry an expression selector the engine would refuse, 1,099 end somewhere other than their terminator, and 24 branch targets do not land on a boundary. Every "garbled" row is downstream of one of those gaps, so the right expectation is that they are **recoverable**: a model fix turns them into either operands (and they leave the tables entirely) or real text (and become translatable). None of them should be treated as permanently unreadable.
- **Engine boundary agreement was measuring the wrong denominator; the opcode model now has *zero* known disagreements on the traced routes.** `1F01` prints a party-member name by reading it through the same byte fetch the tracer hooks, but out of a *string buffer*: the PC restarts at 0 and counts up in twos, one event per character, then execution resumes just past the `1F01` token. Verified end to end at `m/MS0017` r02 0x9E (`1f 01 00 00 04 ff`, four events spelling 葛城史人, resume at 0xA6) and across all 74 runs: every pc is even and ≤ 8, every character decodes as cp932, and the strings are 葛城史人 / 橘由宇香 / a counter. **No record holds those addresses**, so scoring them against our tokenisation said nothing about the model -- and it is the whole reason the figure sat at 98.4%. `giten/trace/core.py` now classifies them (`NAME_KIND`), strictly: a `1F01` token must sit on one side of the run, the body must be even PCs ascending from 2 that decode, and execution must resume inside a record. Of 18,683 events on `jp2` + `jp-friends`: 252 name-buffer, **0 model errors**, 29 script-end (a v1 tracer limitation -- it read the context after `exec_token` returned and the engine had already cleared it; v2's `pc0` fixes it, but no v2 trace has ever been captured), and 10 excursions no `1F01` bounds, left as disagreements because their cause is unproven (`m/MS00D8` r00; the token before them is `1F86`, which is `push $1; push $1; call 0x00434740` -- a conditional branch, so it cannot be the printer, and the RECID logged there is stale). **So "pull on the opcode model to raise agreement" is finished work: the ceiling it can reach is the number it is already at.**
- A decoder bug found in the same pass: `locate` rule 1 accepted *any* text token ending at the logged pc without checking the character, which shadowed rule 2 (a branch landing on that pc). At `m/MS7F04` r07 0x2A the engine had jumped onto the `18` opcode starting there and the two text bytes ending there were charged with the disagreement. Those were the last 3 "model" errors and they were never the model.
- **`1E C4` reads one expression, not two** (fixed 2026-09-06). Found with no trace and no playing: of 25,346 rel16 targets corpus-wide, 25 do not land on a token boundary, and one of those is in `m/MS00D8` r05 -- a record the engine executed 187 times on the traced routes. `1E C4`'s trampoline is `push $1; call 0x00433860`, which forwards to `0x004335E0`: that reads two u8 (`0x004335A0`), then calls `0x004335C0`, which reads an expression **only when its argument is 0**, then always reads one more. Mode 1 therefore takes `u8 u8 expr` = 6 bytes, and 0x25 + 6 = 0x2B is exactly the branch target that missed. Its sibling `1E C3` is the same shape with mode **0** and does read both, so the table was right for it -- that pairing is the control. Same family as the `0x14C`-`0x151` fix, missed because it reaches `0x004335E0` through an extra hop. `ok`/`stray`/`unimpl`/`untiled`/`impossible` all unchanged; engine boundary agreement 98.40% -> 98.43% on `jp2`/`jp-friends`.
- **`tools/opcode_operands.py` reports operand *counts*, never order.** `spec()` emits `["u8"]*a + ["u16"]*b + ["u32"]*u + ["expr"]*c`, so any opcode whose real layout is not u8s-then-u16s-then-exprs is printed as a mismatch. `0x00B` is the worked example: the tool says `u8,u8,u16` against the table's `rel16,u8,u8` and looks like a bug, but `0x00430008` is `push $1; push $0; call 0x00434850`, whose first call `0x00434680` is `jmp 0x00433EC0` -- the rel16 reader -- before `0x00434780` reads the pair. The table is right. The corpus says so too: with the displacement in the first slot 1,263 of 1,267 targets land, with it last only 46 of 96 do and 1,174 fall out of the record entirely.
- **Two disproven hypotheses, recorded so they are not re-tried.** (a) *`1F0D`/`1F0E` take no operand.* The bytes look like it -- `1f 0d 1f e5` reads naturally as two opcodes, and it moves `untiled` 74 -> 38 -- but the handler walk says both read an expression, and `impossible`, the counter that cannot improve by accident, gets **worse** (43 -> 50). Rejected. (b) *Expression selector `0x02` is a u16.* It scores better on the branch oracle (25 misses -> 13), but selector `0x02`'s handler `0x00436B3B` calls `0x00438FE0`, which is `0x00438EC0` = two u16 fetches with the second shifted left 16, i.e. a real u32. The gain is an accident: `0x02` occurs 13 times in the whole corpus, 12 of them in `m/MS6F00`/`m/MS6F1F` (byte-identical duplicates), and 10 of the 12 "fixed" misses are in records that never tiled. A rare selector shortened by two bytes reshuffles boundaries in already-broken records. **The branch-landing oracle can flatter exactly like `stray` and `overrun`; check whether the records it fixes were sound to begin with.**
- **The other 24 boundary misses are in records nothing has ever executed.** `m/MS610D`, `m/MS6200`, `m/MS6F00`, `m/MS6F1F` contribute 0 traced events between them, and `m/MS6F00`/`m/MS6F1F` are byte-identical, so 25 sites are 17 distinct and 16 of those are unexecuted. Whether they are code the routes never reach or data tokenised as code is open; the `1E C4` result shows the branch oracle can settle such a case when the record is real code, and the `0x02` result shows it cannot be trusted alone when the record is not.
- **The tag-`00` spans that reach the `japanese` rule are data, not text -- but not one kind of data.** Two were run down on 2026-09-06 and neither is "garbage" in the sense of meaningless bytes:
  - `m/MS0007` r35 and its siblings (`ｮｭｱｲｳ`, one half-width kana per span): `1FA7` at 0x0192 is typed `rel16 + expr + expr` and consumes 8 bytes, but the site is `1f a7 | 91 01 | 00 b0 00 af 00 ae 00 ad 00 b1 00 b2 00 b3 | 04 ff` -- a **variable-length list**, of which the model claims the first two entries and the other five become NUL-opcodes and one-byte "text". The values `b0 af ae ad b1 b2` are the same ids the neighbouring `1F60 00 XX` opcodes take, so they are operands beyond doubt. Same shape as the `0x103`/`0x104` fix (a list where the table claimed a fixed count).
  - `m/MS001F` r02 (`辞書５`, `{01:00}`, `{04:FF}`, `d`): 11 bytes sit between two `1E BE` tokens (`1e be 00 01 72 | 01 00 00 00 06 00 00 04 ff 00 64 | 1e be 01 03 05`). `1E BE` is typed 3 u8, fixed size 5, and the walk *does* consume exactly that -- so unlike `1FA7` the fault is not a short read of a known opcode; nothing claims those 11 bytes at all. Cause not yet named. `m/MS002B` r02[89] (`d{03:00}`) and `m/MS0059` r04[19] (`{03:00}d`) are the same run.
  - Consequence for the tables: **`m/MS7F05` is a dead dictionary.** It holds exactly one entry, `辞書５` ("Dictionary 5"), and all 7 apparent `{06:xx}` calls in the corpus are the `06 00` of that data run being rendered as a pool call. Nothing on screen ever prints it, so it is deliberately left untranslated.
  - The engine trace cannot adjudicate any of this yet: none of these records has ever been executed on a traced route (`m/MS001F` has 3,603 traced events, all in record 5). Raising boundary agreement above today's 96.83% would settle them only for records the routes actually reach -- for these, the next step is either the `1FA7`/`1EBE` handlers under `tools/opcode_operands.py`, or a route that enters them.
